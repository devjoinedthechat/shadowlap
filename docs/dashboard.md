# Dashboard

`shadowlap dashboard` opens your recordings in a browser: the same store the CLI and the terminal UI use, with more room to read.

```sh
shadowlap dashboard              # opens http://127.0.0.1:4777/#token=…
shadowlap dashboard <run>        # opens a run directly
shadowlap dashboard <run> --call 17   # at a call
shadowlap dashboard --no-open    # print the link instead
shadowlap dashboard --read-only  # look around, change nothing
```

## What you see

- **The shell**: a sidebar with the project, **Search or jump to** (⌘K or Ctrl K), Overview, Runs, Compare, Fixes, Tests and Training, the most recent runs as a tree as deep as each family goes (a replay or a fork a step in under the run it came from, so a fork of a fork sits under that fork, as the Overview's grid nests it; a lineage deeper than four steps keeps to the fourth, where a run's id and time still fit), each saying a failure as Runs' Status does (*lost at #9*, *diverged at #3*), or *inconclusive*, in amber, where a check couldn't be decided, each by its id and when, then its about line and only what needs a look (*lost at #9*), and Settings; a top bar with what this dashboard is (*dashboard*, *team* with a [team store](./team.md), *read-only* or *exported*, with why on hover), where you are and, while a run records, a live chip, kept while the server can't be reached (when a recording ends, recorded from a terminal or anywhere else, a toast says so on whatever page is open: *Recording finished · 01M53JE2Q0 · 32 calls*, or *interrupted* when it stopped before its end; a run a dashboard job made says how it ended in the job's drawer instead); a status bar with the store, the run count (attempts counted apart), whether it is in sync, the address and the version (with a team store, its name and its last sync, or *setting up* while its setup is under way). Dark only. Below 1000px the sidebar is a drawer behind the menu button.
- **A run's id and its about line**: a run is named by its id on every page (its heading, the crumbs, which carry its lineage, the sidebar, Runs, Compare, Search or jump to, the Overview), and one quiet line says what it was about. It is worked out from the run and never edited: for a recording, the first sentence of the first thing the user asked (in a run of several agents, what the agent under test was asked first; for a batch, its input, as *inbox 2026-09-30*); for a test replay, its golden; for a replay or a fork, what it changed, the call it changed written with # (*override #16*, *HTTP 529 #19*, *rescued #5*, *clean replay*), so in a tree a child shows only its change; for an attempt, what it asked again (*resampled #5, attempt 2*); for an import, its file or trace (an import of several files shortens to *a.jsonl and 1 more*); otherwise its command. Where it has one line it is fitted to the room it gets at whole words, its first words and its last with *…* between (*Ticket T-8812 … arrived damaged*), keeping a ticket or order number rather than a UUID; it gives its place up rather than show part of a word, and what a replay or a fork changed is never shortened, but for a field set by its path, which keeps its last parts with the value and the call (*budget_tokens=4096 #17* for *thinking.budget_tokens=4096 #17*). In the sidebar, a test replay's status beside it (*check failed*) gives way before its golden's name does. It quotes what the run recorded, so a copy that leaves the store (an HTML file, a share link) works it out from that copy, with the project's redaction rules applied. Labels stay chips beside it, for meaning and filtering, never a name. Runs' filter matches it.
- **Search or jump to**: every page, This run's actions, the runs (the newest 500, each by its id with its about line as the hint, and any other run by its id, typed in full or its first characters), the goldens, each with its last verdict (*passed*, *failed* or *inconclusive*, a gate's with its tally and bound), with **Update goldens…** when any diverged, which opens its dialog on Tests, and, from three characters, what the runs recorded (prompts, responses, tool arguments and results; up to six matches, two per run). Matches in recordings, forks, tests and captures come first, however many attempts match too: an attempt (`--repeat`, a blame probe, a verify attempt) replays its run's text, so it shows only for a run with no match of its own, and the attempts of one run count as that run. Every typed word must match. The dashboard keeps the search index up to date beside everything else it serves, in slices of about 50 ms while it is idle; while another command writes the store (`gc`, a pull, an import), it waits a tenth of a second at most and tries again later. So a search answers at once from what is indexed, and no other page waits for the index longer than a slice. A search first takes in what a run still recording said since the last one, so its newest calls are found as they arrive. Until the index has read every run (on its first start over a store of thousands of runs), the palette says how many runs it has yet to read and asks again until it has. While the server can't be reached, its field searches runs and pages, and an action that starts a job stays in its place, dimmed: *paused: the server can't be reached*.
- **Overview**: this week at a glance, in your own days (this week is the last seven, today included). It leads with outcomes, each against last week: failures reproduced (blame replays a failure exactly before it probes; a failure is a fix, however many of its runs were blamed, as the fixes funnel counts it) with how many fixes are still open, fixes verified with how many changes were rejected before they shipped, tests passing over the goldens on disk with each of the others by its newest result as Tests shows it (*5 / 7 · 1 failed · 1 not run yet*; amber when the only ones not passing are inconclusive), and when they last ran, and what was spent live, with what replaying saved after it (not re-spent, and time not waited); with a [team store](./team.md), what teammates' pulled runs spent counts too, as the team's (a pack you unpacked and a capture don't: that traffic was paid for where it ran). Then every run of the week as a row of calls colored by origin, grouped under the recording it came from on one scale, so a fork's replayed prefix lines up under its parent (past 60 calls a cell stands for a range; the cell where a fork left is outlined; a recording grows in place); **Needs a look**, most urgent first: a [team store](./team.md)'s setup left unfinished (**Continue** opens it), an applied fix that doesn't hold, failing tests (**Fix** to the fix that holds the failure, else **Open** to the failing run), then [injection tests](./injection.md) a planted instruction got through, in red, and those it influenced or that showed too little to say, in amber (a golden's injection gate is its test's line, not one of its own), and [error-path presets](./error-paths.md) that failed, each opening the attempt that shows it; inconclusive tests (an amber mark, with **Run more** when the gate ran out of attempts, **Run again** when its injection test showed too little to say, and **Update** when a judge check of a golden that replays offline has no verdict yet, all to Tests, else **Open**) and presets left inconclusive; failures with no fix yet (open fixes, with **Fix it**, or with **Open** and where to look when blame found that no answer of the model's lost the run; and failed runs never blamed, a fork that failed as much as a recording, by their id and what they were about, with **Run blame**); in amber, a [preview of a change](./decisions.md) whose flagged runs no session of that change has settled since (one that asked them again and flagged none, or whose verify accepted them, as a migration to a model after a preview of it), opening the first at the call whose decision changed; verified fixes waiting to be applied, with **Mark applied** for one that has no patch, as its page has it (one verified with request fields set, as `--set temperature=1`, says to make them in your agent first); how many behaviours seen in production no golden [covers](./coverage.md), opening a run of the newest; and, with a [team store](./team.md), how many runs are only on this machine, counted as Settings → Store and `shadowlap store show` count them (by run: a run counts once when it, or an attempt filed under it, isn't in the store yet), whose **Push** opens Runs with **Local** picked, those runs alone, each with the `local` tag; on a read-only dashboard each line says **Open**, since nothing runs there; past ten of a kind, one line says how many more there are and opens the page that lists them; **Today**, with tests counted as the tile counts them, each golden by its newest result (the test replays that ran today on hover), and the blames that ran today (their probes on hover); the week's calls by origin; where the prompt cache stopped hitting, by the Context view's rule, with the tokens sent again; how far each failure got towards a fix; what was spent and not re-spent each day, as a chart or a table; and the latest activity. **Watch live** opens a recording in progress.
- **Runs**: every run in a table, a page at a time, one row a run: its id, then what it was about with its labels as chips, its calls by origin, calls, spend, outcome (a fork's says what came of its writes, *forked · 2 writes blocked*, or names the check it failed under *check failed*) and when; with chips by kind (recordings, forks, clean replays, tests, captures, failed) and their counts, a filter (every word must be in the run's id, about line, kind, labels, command, source or revision), and sorting by calls, spend or time. What only adds to a row gives way, measured, while the about line would get too little room: first the calls by origin, then the labels, then who made it; only then, and on a tablet or a phone, the about line goes under the id. Attempts (`--repeat`, blame, verify and the [error-path presets](./error-paths.md)) are bundled under the run they came from rather than listed, and so are a golden's when one test session replays it more than once (`repeat`): one test run, the attempt its result shows, whose checks count every attempt (*5 of 5*). A run imported from a capture shows the file it came from where a command would be, and its cost as captured rather than spent: that money was spent where the traffic ran. Above the table, twelve weeks of days, a column per week, shaded by how many runs each day had of what the chips and the filter match, so with **Failed** picked it shows when something started failing. Click a day, drag across several or Shift-click to extend, and the table and the chip counts follow; the arrow keys move between days, Enter picks one, Escape clears. With **Failed** picked and days chosen, **Find the commit** bisects from the first failure of those days, between a commit where it still worked and its own, offering only commits this checkout has: a teammate's runs can name commits of theirs, and a failure whose own commit isn't here is bisected up to HEAD. A failure at the repository's first commit (or the oldest a shallow clone has) has nothing before it to search: the dialog says so, and bisects from the first failure of those days that started later, or offers no search when none did. With a [team store](./team.md), the **Local** chip lists the runs only on this machine, as Needs a look counts them. Tick runs to label, pack, export (one dataset takes at most 500 runs), compare or delete them together. **Delete** names the attempts bundled under the runs ticked, which go with them as `shadowlap rm` takes them, and counts them when it is done; it leaves alone a run still recording, one a replay in progress reads from, and one with an attempt still running, and its dialog shows the `shadowlap rm` command (for a long pick, the first ids and how many more, with **Copy the whole command**). **Pack** asks for a folder first: one run goes into `.shadowlap/exports/<id>` unless you name another folder inside the project; several go into a folder each, named by its id, inside `.shadowlap/exports` or the folder you name, in one job whose drawer lists every folder (at most 100 runs at once). **Dataset** says how many redaction rules its copy applies and shows the `shadowlap export dataset` command it runs, with the file it writes. A run whose recorder stopped before it ended (killed, or out of memory) reads *interrupted*, and is deleted, packed and pushed like a run that ended. A run ticked and then deleted elsewhere leaves the selection. With a [team store](./team.md) set, the table shows who made each run as their avatar, the name on hover (yours marked *you*), shows a teammate's run at what it cost where it was recorded, tags `local` the runs only on this machine (and a run whose attempts are), and offers **Pull** above it and **Push** for the runs ticked, with the attempts bundled under them (one still recording goes when it ends); the status bar names the store and when this machine last pushed or pulled. A link can open Runs filtered: `#/runs?q=<words>&type=failed`, or `type=local`.
- **Import a capture or a trace** (on Runs, or from Search or jump to): drop or pick a file, and the format is guessed from its name and its first bytes, and can be changed: `.har` is HAR; a `.json` file is OpenTelemetry when its name says otel, otlp or trace and a VCR cassette when it says cassette or vcr, and otherwise what it starts with decides (a HAR log, OTLP spans, a cassette's interactions, a nock recording or a Shadowlap capture), nock when that says nothing; a `.jsonl` file is LiteLLM unless its name or its first line says OpenTelemetry. YAML is refused with the reason. **Use a sample: otel-traces.json** picks the trace the dashboard ships (one agent run as an OpenTelemetry collector exports it: two model calls and the tool call between them), dated to end now; **Import** then brings it in as any file you pick. Or give a Langfuse, LangSmith, Phoenix or Logfire host and trace id (a UUID for Langfuse and LangSmith, or for Langfuse also 32 hex characters, as on the trace's page; 32 hex characters for Phoenix and Logfire), and for Phoenix the project, which starts as `PHOENIX_PROJECT` or `PHOENIX_PROJECT_NAME`, else `default`: the CLI reads the trace with the keys already in the environment the dashboard runs in (`LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`, `LANGSMITH_API_KEY`, `PHOENIX_API_KEY` when your Phoenix asks for one, or `LOGFIRE_READ_TOKEN`), and they never pass through the browser. Logfire is searched back 30 days; an older trace takes [`--since`](./cli.md#traces) in a terminal. The job runs [`shadowlap import`](./cli.md#import) under the name of the file you picked, and its drawer links to each run it made, or past three, to Runs filtered to them.
- **A run**: what it is and where it came from, its command, revision and timing, and why it failed (the check it failed in the CLI's words, with the arguments it names and how a tool's calls were fenced, as `send_email called 1 time, but called 2 times (2 blocked)`; the agent's exit; where a test diverged); a capture whose file kept no times (nock, VCR) shows no duration, and one of the model calls alone says its tool calls were not captured; its counts first (calls, replayed, live, fenced, upstream requests, spent), then what replaying saved: not re-spent, and the time not waited (each replayed call's duration where it was recorded). A recording unpacked from someone's pack says *recording · from a pack*; a teammate's run pulled from the [team store](./team.md) is a recording like any, with the requests it sent and what it spent where it was recorded, by whom (*≈$0.0030 spent · by maya*, and the same in Provenance's Upstream row), and its replay asks first, as a pack's does. One banner says how an [error-path preset](./error-paths.md)'s attempt came out, by the verdict of the session that decided it (an earlier session's attempt keeps its own once the presets run again), then the preset and the golden it ran on, which attempt of the preset it was and what the preset played in where (*failed · tool timeout preset on goldens/list-inbox, attempt 1 of 1: list_inbox (#2) timed out, played in by the preset · writes stubbed*, with **Tests →** for a golden's), wrapping rather than cut; its status chip goes by that verdict, and the meta line says why it failed, the agent's exit with its last line, how it forked, what the flag did and what came before it ("answered with HTTP 529 by `--fail-at 19=529` · nothing sent", "tool #16 overridden with `--override 16=@policy.json` · 15 replayed and #16 overridden before it"), where blame found it lost (with the fork it rescued and its fix), which checks it passed, what was not recorded, or that it failed and was not blamed yet. The header's one lime button is the run's next step: **Open the fix** for a failure a fix holds (its hover names the fix, and the banner says how it stands, *fix open* or *fix verified*, where it linked it), **Run blame** for a failure never blamed (not on a run that made no model call, or one that was stopped: blame needs a run that fails again as recorded), **Compare with parent** for a fork or an attempt, the banner's **Add normalizer** for a test or a replay that left its recording on a value made anew on every run, and **Replay** only where nothing needs doing; every other action stays beside it, plain, and the banner doesn't offer the step again. A fork that failed, by its check or its agent's exit, says *failed* beside its id as any run that failed does, keeps the banner that says how it forked, and leads with **Run blame** (or **Open the fix**, once a fix holds it); until it is blamed, it counts among the failures not blamed yet. An attempt of blame, verify or `replay --repeat` says it is one (*blame attempt*, *verify attempt*, *repeat attempt* above its id; the fork blame rescued a run with is its *rescued fork*), and its banner says how it came out first (*passed*, *failed*, *inconclusive*, or *interrupted*), then what was asked again and which attempt it is of those made (*failed · resampled #5, attempt 2 of 4: the model was asked #5 again, the request as recorded · writes stubbed*; *passed · verify · target, attempt 1 of 12 · code 35034be: the change it verified is in the request (~ $.system)*, or the flag a `--model` or `--set` change was made with; *replay --repeat 5 at #16, attempt 2 of 5: forced live with `--live-tool lookup_policy`*), then how the writes after it went and, for one that could not be decided, the check that couldn't be. A gate that settles makes fewer attempts than its limit, and the count is of the attempts made. The banner wraps rather than cut its words, and links back to the attempt's probe on its fix's Blame step or to the verdict it counted towards, and to all its attempts in Forks; it offers no Run blame, since its failure counts towards what made it. A replay an injection test, a model's scoring or an error-path preset made keeps its fork banner. A fork whose only flag is `--writes` forked where its request changed, and its banner says that. A test that diverged on a value made anew on every run says what the value looks like, with **Add normalizer** (it adds the rule and runs the golden again; once the rule is in the config, the banner says *normalizer added* and links the replay that passed) and **Update golden**, which asks first, as on Tests. When the rule alone can't make the replay match (the request carries a field the recording never had, as a per-run id added since), the button reads **Add normalizer and update…** and asks first too, in the Tests screen's dialog with both commands, since the golden is then re-recorded live after the rule; once the rule is in, **Update golden** stays beside *normalizer added* until a replay of the golden passes. A fork opens at its divergence; **Show diff** shows the request that changed, and the normalizer to add when the change is a date or an id: for a test that diverged, the value its banner found made anew on every run, what it looks like and its normalizer, so the diff never says that no normalizer is suggested where the banner offers one.
- **How a run stands**, worked out once, by the server, for its page and every list: a test of a golden that may fork is judged by its checks, not where it left the recording (its banner lists the checks it passed and where it forked, or the check it failed); a run a fix lists among its failing runs (verify's target) fails that fix's check here and in Runs, with how the fix stands; a run whose agent exited with an error reads *failed*, one that failed a check *check failed*. A run that stopped before it ended (Ctrl-C, a kill, a crash, a recorder that went away) reads *interrupted* in grey after what it is (*recording · interrupted*, *fork @3 · interrupted*), ended at its last call: it stopped, it did not fail. Its page says so in a banner (a fork's banner says how it forked, and its header that it stopped), and, open while it recorded, ends on *Recording interrupted*; Runs, the sidebar, the Forks view (a `--repeat`'s attempts too), Provenance's lineage, the Overview and the activity feed say *interrupted* too.
- **The origin strip**: one cell per call, colored by what happened to it (replayed, live, overridden, injected, failed, blocked, stubbed); the legend lists those present. *Injected* is a failure Shadowlap answered with instead of the provider, from [`--fail-at`](./interventions.md#inject-a-failure). The fork and the call blame named are flagged. Click a cell to open that call; from the keyboard the strip is one stop for Tab, ← and → (Home and End) move between its cells, and Enter opens the call. In a run of more than 360 calls, each cell covers a range of calls and takes the color of its rarest origin, so a single blocked write still shows; hovering it counts the range.
- **Scopes**: a run made with `scope()` gets a chip per scope, nested ones included, with counts; picking one dims the strip outside it and narrows every view to it. The line beside them gives the `shadowlap blame --scope` command for the scope picked, or else for the one that acts (the scope that hands work to a nested one, or makes the most tool calls), not a model that plays its user: with one other scope that calls no tools, it says so (*Blame only the agent, not the customer it answers*).
- **Views of the run**, beside the inspector (`v` cycles the first five). Every mark selects its call. The lists draw only the rows in view, so a run of 50,000 calls scrolls, steps with `j` and `k` and switches views as quickly as a short one; while a long run is on its way, the page says *Loading the run…*:
  - *Calls*: every call with its kind, name, origin, tokens and time; a model call names the tools it asked for, a tool call shows what it returned on a second line (or that it was blocked, stubbed or failed), a clock or random call the value it gave, a model call that asked for no tool what it answered on a second line (the agent's final answer), and a person's answer the agent read ([what a person types](./sdk.md#what-a-person-types)) is tagged *input*. A replayed call's time is its recorded duration, in grey, because the replay did not wait for it (a clock or random read records none, so its time is blank). Filter by origin (*Fenced* holds the writes blocked or stubbed after a fork) or text; each row has a fork button.
  - *Turns*: each model call with its tokens and stop reason, what it said, and the tool calls that followed it, grouped by scope.
  - *Context*: tokens per model call, split into input read from the cache, written to it and uncached, with output below, as a chart or a table; past 360 model calls a bar stands for a range of them, drawn at its largest context, and holds a miss when any call in it is one. A call is flagged where the cache missed: it read less from the cache than the previous model call in the same scope and conversation sent in all, by 1,024 tokens or more. A miss sends the prompt again and writes it to the cache anew, so the calls after it read it from there: a fork's change costs the call it forked at, and the note says only that call missed. When every call after the first misses, something early in the prompt changes on every call (a time, an id): the most expensive bug an agent has. An agent that never caches its prompt sends its history again on every turn, so every turn after the first is flagged, and the view says the cache was never read.
  - *Timeline*: every call on a clock, colored by origin, with the first token of streamed responses marked, scope by scope; how long model calls and tools took, the longest call, and what ran at once.
  - *Forks*: the run's family: its recording, every replay and fork of it, with a line on what each did; a test replay of a golden that may fork says where it forked and what it did live (*test · forked at #3 · 25 live · ≈$0.018*), and one that diverged where its golden may not, where it diverged. Attempts of one `replay --repeat` are bundled with how many passed, and how many were interrupted (in grey: an attempt stopped before it ended neither passed nor failed), and so are a golden's attempts in one test session (*test · refund-over-limit*); a golden with a gate says what the gate made of them, as Tests does, with its verdict, tally and Wilson bound, and its rule once under them. Blame's attempts are bundled per probe under the run they replayed, the probe blame named marked *blamed*, and verify's per run under each change it checked, named as the fix's Verify step names it, its icon saying how the run came out (a verdict that doesn't count for the fix says so, *doesn't count*, with a plain icon); each bundle says its verdict as a gate's is said, the word, the tally and the Wilson bound (*rescued · 2 of 2 · rate >= 0.34 (95%)*), then what its attempts spent, a verify's then the change it checked and how that came out (*fixed · 12 of 12 · rate >= 0.76 (95%) · ≈$0.046 · repair candidate 3 · accepted*), and each rule they were decided by is stated once in the family. Each opens its fix at that step, a verify at its verdict. An [error-path preset](./error-paths.md)'s attempt that failed reads *preset failed*, and one that couldn't say *preset inconclusive*, each by the session that decided it. Under a run several fixes share, such as a good run every repair kept, each bundle names its fix. The fork blame rescued a run with stays a fork of its own.
  - *Provenance*: the run's record (its about line whole, with where it comes from; command, revision, times in UTC, models as recorded, provider, upstream requests, origins), its lineage with how each run stands (what a failed one failed, in red; an interrupted one in grey) and its revision, what a copy made now applies, each call's fingerprint and blobs, and its labels and notes. **Copy show --json** copies what `shadowlap show <run> --json` prints. What a copy would mask is counted as Settings → Redaction's preview counts it for a pack (each value once, however many requests send it again), apart from the dashboard's own work. When a path rule masks what calls got back, which only `export html` and `dataset` do (a pack keeps it for its replay), it gives their count too; when the rules also match values a pack leaves as they are (numbers, which a pattern never rewrites), it says how many stay as they are. When a rule takes too long on the run's text, it says the values weren't counted, with why on hover; while Settings → Redaction's previews hold every thread it uses, it says they are being counted, and asks again until they are.
- **The inspector** for the selected call:
  - *Conversation*: the conversation exactly as the model saw it at this call, with tool calls and thinking blocks shown. It works the same for Anthropic, OpenAI (Chat Completions and Responses) and Gemini requests. **Format JSON** lays out tool results that are JSON; on a fork, **Jump to change** opens the message the fork changed. For a call answered with `--fail-at`, it says the request was never sent. A tool call shows its arguments and its result, then the model call of its own conversation that asked for it (in a batch of many conversations, which one), with **Show its conversation**.
  - *Response*: the response as text and tool calls. **Play** replays a streamed response at its recorded pacing (1×, 2×, 4× or instant). *Raw* shows the stream as recorded. For a tool call, the recorded result or error.
  - *Request*: the stored request (or tool arguments) as a collapsible tree.
  - *Details*: origin, outcome and HTTP status, model, stop reason, token usage by cache tier, cost, latency and first token, size, retries, fingerprint and occurrence, response headers, and notes.
- **Labels and notes**: label a run from its header (`bug`, `good`, `refund-flow`), or several from Runs, and leave notes on a call in its details.
- **Tests**: every [golden](./ci.md) on disk (the packs in `goldens/` and those the config's `tests` name) and how it did. A verdict leads: how many fail by their last results (or, with none failing, how many are inconclusive, in amber: a [gate](./gating.md) that ran out of attempts between its bounds), the first one named, with the line of the newest session that ran them all (CI's, or **Run tests**): its command, revision, time, its own passed and failed counts and upstream requests, *running* while its process is there (started from this dashboard, another one or a terminal), *interrupted* when a signal stopped it, *did not finish* when its process was killed. Goldens run again on their own since (by **Add normalizer and re-run**, say) follow it, as *since: refund-in-limit passed*, each with its result on hover. Then a row per golden: its name with its mode under it (`replay`, `fork ×5`, or `fork · gate` and `fork · history` for a golden with a gate, with what it means on hover) and where it came from, its checks, each marked by how its last result came out on it (✓ passed, a judge check's with where its verdict came from: the recording, free, or the judge asked live, with what that cost; ✗ failed, with what it found and, for a golden run more than once, how many attempts passed it, unless some were carried over from an earlier session; ? inconclusive, in amber, with why; – not applicable; no mark on a check not tested yet: before the golden's first result, when its last test couldn't run it, or when the check was added to the config since), its result at each recent revision of a session that ran them all (why it failed on hover, a ring where it was updated; a golden run again on its own shows in the column of its commit, with changes on top named on hover, and adds no column of its own) and its last result (*passed*, *updated at `<rev>`* after an update; a golden with a [gate](./gating.md) by its verdict, then its tally and Wilson bound, against history with its baseline, and the pass rate's interval drawn against the gate's two rates or its baseline, each gate's rule stated once under the table, beside its goldens' mode, and where two rules share a mode, with the goldens each decided); under it, how the golden's [error-path presets](./error-paths.md) came out, opening the attempt that failed, and a golden whose presets ran but whose replay hasn't yet says so, never *not run yet*; a row opens the golden's latest run. The table fits its panel at every width: with less room the oldest revisions give way, then the checks move under the golden's name, and on a phone the revisions become a strip there too, while the last result keeps its width. ## What a run's page is worked out from

Besides each call as recorded, the run's endpoint (`/api/runs/<id>`, which the page and an [exported copy](./cli.md#export-html) read) works out the following for it.

- **Conversations.** A run can hold many: an overnight batch works through forty tickets in one process, and a multi-agent run has one per agent. A model request continues a conversation when it extends that conversation's latest request in the same [scope](./sdk.md): the messages (Gemini's contents, the Responses API's input items) sent last time come first again, with the answer and what followed it appended. Cache breakpoints, thinking blocks and thought signatures that an agent moves or drops between requests don't count, and neither does a system message that only carries the time. An agent that edits its history still continues its conversation: one that drops its oldest turns, by the tool-use ids it still carries, and one that strips a reminder from an earlier message or completes a prefilled answer, by the last answer it carries right after the history it kept. A request that continues no conversation starts a new one; so does one that repeats another conversation's request word for word, unless that request failed and this is its retry. A tool call belongs to the conversation of the model call that asked for it, matched by name and arguments in its scope, with the tool-use id the provider gave. A call no model asked for goes with the tool that was running when it started (the HTTP request a tool sends), else with the model call whose tools have not all run yet, else with the next model call (the ticket fetched before it). A call's *Conversation* is its own conversation as it stood at that call, never another ticket's or another agent's.
- **Where the prompt cache stopped hitting.** A model call misses when its cache read is smaller than the previous model call's whole input (uncached, written and read) in the same scope and conversation, by at least 1,024 tokens; the tokens sent again are the difference. A conversation's first call is never a miss, so a batch doesn't flag the start of every ticket. Every call whose cache read is known is judged: Anthropic and OpenAI report it, zero included, and Gemini leaves it out when it read nothing. An agent that never asks to cache therefore shows each turn's history as sent again; a server that reports no cache at all (a local model behind an OpenAI-compatible API) shows no misses. The share of input read from the cache counts live model calls.
- **Time not waited.** A replayed call is answered from the recording at once. The time it saved is how long the recording waited for it, found on the run it was replayed from, or further back for a replay of a replay; each replayed call carries it, and the run sums it.
- **What was not recorded.** The hosts the [network guard](./how-it-works.md#the-network-guard) saw the agent reach without Shadowlap, and the tools `shadowlap init` finds in the project without a declared effect that the recording never saw. They ran for real, and a replay runs them again.
- **The fork and what made it.** The call a replay forked at, and the flags it ran with, as the replay kept them on the run: `--fail-at 19=529`, `--override 16=@policy.json`, `--inject 15=Prefer sources from 2026.`, `--model 15:claude-opus-5`, `--set 15:max_tokens=2048`, `--inject-result`, `--prompt-from`, `--diverge-at`, `--live-tool`, `--writes stub`. Each is shown in a short form: an override read from a file is named by the file, one given inline shows the result its call recorded, and a long instruction is shortened. The run also keeps each flag exactly, so the fork menu can make the fork again; a copy of the run (`pack`, `export html`) keeps only the short form, masked by the redaction rules. A replay made before Shadowlap kept its flags shows the ones its calls reveal.
- **Blame and checks.** A blamed run names the model call that lost it, counted among the model calls of the blame's scope ("model call 5 of 6"), and the fork that blame rescued says it was rescued. Each [outcome check](./ci.md#outcome-checks) is counted over the attempts it ran in: "issue_refund never called · 5 of 5".
- **Each call's own record.** Its fingerprint, the hashes of its stored request and response, and for a tool call its result in one line ("stubbed …", "blocked").
- **The models.** Each model the run's calls named, as every view of the page names it: the id without a date stamp (`claude-opus-5`). Provenance shows a dated id the provider answered with on hover.

A run imported from someone else's pack carries what they recorded about it; anything malformed there is left out rather than shown.

## Actions

Labels, notes and actions run only from a dashboard started with `shadowlap dashboard`; elsewhere their buttons say why they are off. **Replay** re-runs the recorded command. **Fork at #n** (or a row's fork button, or `f`) offers what the terminal UI's fork menu offers for that call, one line each with its flag: at a model call, inject an instruction (always as the user), switch the model, fork with your changed prompt, an HTTP failure (`--fail-at`) or diverge; at a tool call, override its result, answer with a tool error, plant a prompt injection (reads only), force it live or diverge; at a recorded user input, answer differently as the user or diverge; and for the whole run, repeat the replay and compare the attempts (`--repeat`), stub the writes, or find the commit that broke it ([`bisect`](./cli.md#bisect), which asks for a commit where the run still worked and offers the ones its command was recorded at that this checkout has, searching up to HEAD when the run failed at a commit it lacks, such as a teammate's; on a run that passed, the first commit after its own that changed what it does, once there is a commit after it; a run that failed at the repository's first commit, or the oldest a shallow clone has, has nothing before it to search, and the item says so instead; a run that failed on its own is replayed with `--fork`, and the dialog says that one live replay decides each commit, which a failure that doesn't happen every time can pass); a fork is made again from its parent, with the flags, command and checks that made it. An action that needs something from you (the instruction to inject, the status to fail with, the model to switch to) asks for it in a dialog first; the inject dialog shows the command it runs. What you type is passed as text, never read as a file. See [Interventions](./interventions.md). A run imported from a capture has no command, so its menu shows a note and one action, **Replay** with your command; that replay records every kind of call, and every fork works on it. **Share** copies the run, each copy a job: an HTML file with the runs it came from and a HAR, which also download; a pack, into a folder inside the project; a dataset for evals, in a format and with the examples you pick; or an OpenTelemetry trace, sent to a collector or written to a file (a file only: it is sent nowhere else). Copies are written into `.shadowlap/exports/` in the project unless a pack names another folder, never through a link that is already there, and the menu says how many redaction rules each applies (a trace carries no prompt text, so only the rules without a path). A run is copied once it has ended. With a [team store](./team.md), a share link comes first, its drawer ending on **Copy link** (the report opens for anyone with the link until it expires, 7 days at most), and a run only on this machine has **Push** in its header, as does a run in the store whose attempts aren't (Push sends them). **Delete** removes a run, with the attempts bundled under it, which its dialog names and its toast counts, as `shadowlap rm` does, and the recorded data nothing else uses.

A failed run that was never blamed has **Run blame** on its page. It blames the run with the check it failed, found the way a replay is judged: the run's own `--expect`, else the entry under the config's `tests` for the recording it replays (the golden a test replayed, or the pack it was unpacked from, through the runs it came from); else the check of the fix it fails in or of a fix its labels point to; else the agent's exit. When the run failed a check none of those give, or nothing says what a passing run must do, it asks for the check. The blame opens the run's fix, or joins one, and links to it. On an open fix, **Repair from here** runs [`shadowlap repair`](./repair.md) from the fix's failing runs, its check and the scope its blame searched (so the repair blames the same calls and reuses that blame), keeping the fix's own good runs (those a repair or a verify of it kept), else the runs labelled `good` that run the same agent (a good run of another agent checks nothing a change to this one touches), else none, with the repairer `repair.repairer` in shadowlap.config.json names, or else your own Claude Code (`--repairer claude-code`); it asks first, since each candidate is tried in your working tree and put back. When the blame of every failing run rescued it from no call, the repair would reuse those blames and end *No fix to try* without running the agent: Repair from here stays but is no longer the page's lead button, and its hover and its dialog say so, and why (no answer of the model's lost the run, since every attempt met a write's recorded error again or the attempts that passed answered as the recording did; blame couldn't settle where it was lost; or no probe rescued it), the dialog without the line about billed model calls. The blame's own next step leads instead: **Blame again** for a blame that couldn't settle (more attempts and a lower bar, as blame's report says) or stopped part way (to the end, without its budget), under the fix's check; **Blame with a stronger model…** for one that asked the recorded model again and rescued the run from no call, which asks for the model first, unless blame found the model's answer isn't what lost the run. The dialog reads the config again as it opens and names the repairer it will ask, whose account pays; if the config names another by the time you confirm, nothing runs and the job says which one it names now. When that repairer is Claude Code and `claude` can't be found on the PATH the dashboard's jobs get (or where `SHADOWLAP_CLAUDE` points), the dialog says so with what to do and Repair stays off, and the server refuses the job: it would blame every failing run and find no one to propose a fix. An API repairer's key can't be checked without asking it, so the repair says why when it couldn't. On a verified fix, **Copy git apply** copies the command that applies its patch by hand, `git -c core.autocrlf=false apply <patch>`, which keeps Git for Windows' `core.autocrlf` from writing a file with LF back with CRLF on every line (a teammate's patch with LF, for a checkout where the file has CRLF, applies only through that conversion, with plain `git apply`), and **Apply the patch** runs [`shadowlap fix apply`](./cli.md#fix) once you confirm, since it changes your working tree. The confirm dialog names every file the patch changes and shows the patch itself. The patch goes in with `git apply`, the recordings the fixed code made are copied into `goldens/` and `shadowlap test` replays them; the button then reads *Patch applied*, and **View the patch** takes the place of Copy git apply. A fix with no patch (verified on the working tree, or with a change of request fields) reads *Marked applied* once applying marks it, its hover naming the change its agent makes, or saying it was verified on the working tree; the activity feed says *Marked applied* too. A patch already in your working tree (a pull request merged it, or you applied it by hand), which `git apply --reverse --check` recognises as `fix apply` does, needs no applying: the button reads **Mark applied**, which copies the goldens it is missing, runs them and marks the fix applied, Copy git apply is gone, and the Overview no longer counts the fix as ready to apply. For a teammate's repair, from the team store, the patch goes in alone, and nothing runs it: its recordings are on their machine, and your goldens aren't replayed against it until you have read it and run `shadowlap test`. A patch that is more than the change its repair verified (another file, a file made, renamed or given a mode, lines its candidate doesn't rewrite) can't be applied from here: the button stays off and says why, Copy git apply is gone, and `fix apply` refuses it. For a patch repaired here, or a teammate's already in your tree, the project's other goldens are replayed offline too: a prompt or a tool description goes into every request, so a golden recorded before the change can diverge on it from the first call. The drawer names each that does, at the call and request field, with **Update goldens**, which asks first and re-records them with `shadowlap test <goldens> --update`. An applied fix whose goldens failed its test holds again once a test session passes every one of them. Applied is this machine's own: a fix a teammate applied is verified here until its patch is in this working tree. A repair or an apply changes your working tree, so it runs alone in its project: it can't start while a job runs your agent from that tree (a recording, a blame, a replay or fork, a test, a calibration), and until it is done any of those is refused with what holds the tree; their buttons wait, with the reason on hover, and Search or jump to leaves Calibrate out. **Run blame**, **Repair from here**, **Apply the patch** and the Tests actions that run your agent (**Run tests**, **Update golden**, **Add normalizer and re-run**) are off meanwhile and say so on hover; any other action that runs your agent is refused with the reason; a job in another project's folder doesn't wait. A repair or a blame that would run a command from someone else's pack asks once more before it does. **Find the commit** is off on such a run, with the reason on hover, since it would run that command at every commit: replay it with your own command first, and find the commit from that run. **Rename** gives a fix a title of your own, as `shadowlap fix title` does.

Each action is a job: the dashboard runs the CLI in the folder of the [project](#projects) it shows, against that project's store, and the job's output streams into a drawer titled with what it does (Replaying, Forking, Repeating, Packing). The command also tells the job what it made, on a pipe of its own rather than in its output: the runs it started (attempts listed apart, since they open as a bundle), where to go next, the files and folders it wrote, and its result (what `--json` would print). So the drawer ends on the outcome and the exit code and links to the new run (**Open run**) or the attempts without reading the text, names the folder a pack went to, and offers a file a job wrote for download. A **Replay** whose request differed from its recording says where, *diverged at #3 · went live · exit 0*, in amber (red when the agent then failed): `replay` forks at the first request that differs and runs live from there, writes blocked, so the run it made is no reproduction. **Calibrate**, beside **Open run**, replays the recording offline and proposes a normalizer for each value the agent makes anew on every run (a user id, a temporary path); its drawer offers **Add it (--write)**, and the next Replay is clean. A fork from the menu says *forked*: diverging where its flag changed the run is what it was asked for. One that left the recording before the call its flag acts on says that instead, *diverged at #3, before the inject at #17 · went live · exit 0*, in the same colours and with **Calibrate**: the calls before it did not replay, so what the flag changed is not the only difference. Closing the drawer leaves the job running: the top bar counts the jobs running (*1 job running*), from every tab and every page, and a click opens the newest one's drawer again. **Stop**, in the drawer while its job runs, stops the command and the agent it started, as Ctrl-C would, even an agent that ignores the signal (it is killed after five seconds), and the drawer then says *stopped*; it asks first while the job changes your working tree (a repair trying a candidate there, a patch being applied). A run it left recording is marked as interrupted, so it no longer shows as live and can be deleted. Stopping the dashboard (Ctrl-C, a kill, or closing the terminal it runs in) stops its running jobs the same way and waits for them; stopping it again while it waits kills them at once. The dashboard the terminal UI opens (`o` in `shadowlap ui`) does the same when you quit the terminal UI or it is killed, and kills its jobs at once when the terminal it runs in closes.

Tests runs its goldens as jobs too, one at a time in a project: while one runs (**Find the commit** on a golden among them, which reads its pack and answers the failure it started from, or a setup packing and testing a new golden), or a test session or the [error-path presets](./error-paths.md) on goldens (`test --chaos`) started in a terminal or another dashboard run (named by their command), **Run tests**, **Update golden**, **Add normalizer and re-run** and **Find the commit** wait, saying what is running, and the server refuses another such job with the same words, from any tab, the palette's *Run the tests* included; a test replay's page disables its **Add normalizer** (or **Add normalizer and update…**) and **Update golden** the same way. Find the commit on a run that is no test replay touches no golden, and doesn't wait. **Run tests** runs `shadowlap test goldens/*` (plus each pack the config names elsewhere), with no shell: the CLI expands the pattern itself, as it does in CI, and the page follows the session as each result lands. Its drawer ends on one primary action, **Tests**, with the replays of the first three goldens that failed linked above it; a run of one golden ends on its replay. **Update golden** (or **Update goldens…** for every one that diverged) asks first, in a dialog that says what happens and warns when a normalizer is the lasting fix (or, once the rule is in the config, that a re-run passes without an update), then runs `shadowlap test <golden> --update`, which re-records it live with writes stubbed. **Add normalizer and re-run** is two commands in one job, `shadowlap normalize add …` for each value that changes every run, then `shadowlap test <golden>`, the second only when the first succeeded; the drawer links to the replay that passed. When the rule alone can't make the replay match, it asks first and updates the golden after it. **Find the commit** runs `shadowlap bisect` from the newest revision where the golden passed under the checks it has now (a pass from before a check was added may be a commit where it already fails that check); without one, after a search from it named no first bad commit, or for a golden marked `fork` (its replays cost tokens), it asks first, offering the commits the golden was tested at, each with its subject and how it did there (*c91d0f4 · Escalate refunds above the limit*), or any other (**Another commit…**, a field beside the list, which stays to pick one from again). As on Runs and a run's page, it offers only commits this checkout has: a golden that last passed at a commit it lacks (a pull request's merge commit in CI, say) asks for one, and one that failed at such a commit is searched up to HEAD. On a run's page, a run that failed only the check of its fix (blame found it failing, though it exited 0), or a check given with its own `--expect`, is searched with that check (`--expect … --fork`), from a commit you pick. A job only names goldens the project has on disk.

Settings changes `shadowlap.config.json` as `shadowlap normalize add` and `rm`, `redact add` and `rm` do, keeping the file's other keys, order and indentation. Each change names the version of the file the page read, so one made in an editor or a terminal since is never overwritten: the page says so and shows the file as it is now. A rule the CLI would refuse is refused with the same words, and every change lands in the activity feed. **Calibrate** is a job that runs `shadowlap calibrate <run>`, with each round in the drawer; when it proposes normalizers, **Add it (--write)** adds exactly those, without replaying again. **Clean up old runs** runs `shadowlap gc --older-than 30 --dry-run`; when it finds runs, **Delete N runs** asks first (Cancel has the focus), naming the attempts bundled under them, which go too, then deletes exactly the runs the dry run listed, or nothing if others match by then. When no run is that old but runs deleted since (with `rm`, or from Runs) left blobs nothing uses or 1 MB or more of unused space in the store, **Free 53.5 MB** asks first, then runs a plain `shadowlap gc`, which deletes no run and gives that back; Settings → Project shows such unused space beside the store's size.

Some jobs take a file from your browser, such as a capture to import. The dashboard keeps it in `.shadowlap/uploads` in the folder of the project it was sent to, readable only by you, at most 64 MB and 32 files at once, until the job that uses it ends; only a job of that project can use it. A file no job used is deleted after an hour, and every upload is deleted when the dashboard stops. Uploaded files are untrusted data: the command that reads one parses it as it would any file you point it at.

More on a run's actions. **Plant a prompt injection** starts from a few sample instructions, or takes your own or a red-teaming tool's payload as text. A dataset from **Share** takes up to 500 runs at once, from Runs; past that, `shadowlap export dataset --label`. A run is copied once it has ended. One whose recorder was killed reads *interrupted* in every copy, as it does on every screen: the pack, the HTML file (with the redaction rules or without) and the trace hold it ended at its last call, so whoever opens or unpacks it never sees it recording, and the store is left as it is. Where jobs can't run (a read-only dashboard), **Share → HTML file** comes straight from the dashboard, made apart from its own work so pages keep answering; one that takes more than two minutes (a redaction rule whose pattern is slow on the run's text, or a run too long for a download) is stopped, naming the rule most likely at fault, and `shadowlap export html` makes it from a terminal.

## Read-only

`shadowlap dashboard --read-only` shows every page and changes nothing in your runs: replay, fork and the other actions, labels, notes, uploads and deletes are refused, and each says why where you would have used it. The top bar says *read-only*, with the reason on hover, and Search or jump to leaves the actions out. Downloading a run as HTML (**Share → HTML file**) still works, since it changes nothing: the file comes straight from the dashboard instead of being written into the project. Use it to show a colleague your runs, or to look around without the risk of a click changing something. It needs an existing store and never creates one, and it leaves the uploads folder alone (even files another dashboard left there); it opens that store the way every command does, which brings an older store's layout up to date and lets search build its index. A dashboard started without the CLI behind it (embedded elsewhere) is read-only in the same way, and its top bar and buttons say to start it with `shadowlap dashboard`.

## Projects

A project is a folder with your agent's code. Its store is in that folder (`.shadowlap/shadowlap.db`), so each project has its own runs, fixes, tests, configuration and activity, and one dashboard serves several: switching projects switches the store it reads, and every action runs in that project's folder, against its store. The folder `shadowlap dashboard` starts in is always one of them, and the dashboard opens on it. `shadowlap dashboard --read-only` and the dashboard the terminal UI opens serve that one store only.

The project at the top of the sidebar opens the switcher: every project on this machine with its folder and run count, marked *current*, *setting up* or *no runs yet*, then **Add project…**. Picking one switches to it and opens its Overview; a job already running keeps to the project it started in, and its drawer says which (*in support-agent*) once the page shows another, its links switching back before they open. While there is more than one project, each has a × that opens **Remove from dashboard** (from the keyboard: ↓ to the project, then Delete). A project whose folder is gone (deleted, or moved, even while the dashboard shows it) stays listed as *folder not found*: its pages say so and offer to remove it, its actions are refused with the reason, and they come back once the folder does.

Switching is for every tab at once: the dashboard serves one project at a time. A tab that still shows the project you switched away from catches up within seconds (at once when you come back to it), and a change it asks for meanwhile is refused rather than made in the other project: the page says so and turns to the current one. It stays on the page it shows when every project has that page (the Overview, Runs, Tests, Fixes, Training, Settings), with whatever is typed on it, so a refused change can be sent again to the current project; a run, a comparison or a fix of the other project gives way to the Overview. A dialog that was open closes, since what it asked about (a folder to record in, a golden to update, runs to delete) is the other project's, and nothing is done in either; one that holds only what you typed (a rule to add, a server's command) stays, and says it now adds to the current project. A first run's confirmation names the project it was asked in, so it is never used up in another.

The dashboard keeps the list in `~/.shadowlap/projects.json` (`SHADOWLAP_HOME` moves the folder; give it as an absolute path). It holds no recordings: for each project its name, folder and when it was added, how far its setup got, and the commands you confirmed for recording there, and the same for projects you removed, so adding one again brings it back. It is written atomically and readable only by you, and keys it doesn't know are kept. Listing projects reads their stores without changing them, so a project pinned to an older Shadowlap keeps working, and a store in a folder you can't write to is still read; one that can't be read at all (a newer Shadowlap's) is listed with the reason. If the list can't be read, or a newer Shadowlap wrote it, the dashboard still opens on its folder and says why it can't list or add others.

### Adding a project

**Add project…** asks for the folder your agent's code is in. As you type, it suggests folders and says what each holds (`Python · uv · pyproject.toml · uv.lock`, `Node · pnpm · package.json · pnpm-lock.yaml`). A folder without project files of its own that holds projects lists them in its place (`~/code/invoice-bot` rather than `~/code`), and typing a project's name finds it there too. A folder without a `pyproject.toml`, `package.json`, requirements file or other project file can't be added, and says so; clicking it lists what is inside. Adding a folder that was a project before brings it back as it was: its runs, its setup where it left off, and the commands you confirmed there. A project's folder is listed once, by its real path: one you moved with a link left at its old path is already in the dashboard, and adding it by its new path moves the project there. A folder that already has runs, recorded in a terminal, opens on its Overview, as when `shadowlap dashboard` starts there.

Suggesting folders means the dashboard lists directories, so it does that within limits a web page can't stretch:

- Like every request, suggestions need the session token; adding a project, like every change, is also refused from another origin.
- They reach your home folder, and roots you add: `"roots": ["/work/agents"]` in `projects.json`, or `SHADOWLAP_PROJECT_ROOTS` (separated like `PATH`). With nothing typed, a root is listed too: when it has no project files of its own, by the projects in it, in its place, as typing its path lists them (a folder of it without project files gives way to the projects one level inside, as `code/invoice-bot`). A root can't be `/`, a system folder, or a folder that holds your home folder. A path that leads elsewhere, through `..` or a symbolic link, lists nothing.
- They list one folder level at a time, folder names and what kind of project each is, and the projects one level inside a folder without project files (in at most 40 such folders, and 25 subfolders of each, looking into the usual places for code first: `code`, `projects`, `src`, `repos`, `work` and the like); never files, and a file gets the same answer as a path where nothing is. A link is never followed to find them. Hidden folders (`~/.ssh`) and system folders (`~/Library`, `~/AppData` and `~/snap` in your home folder, `node_modules` anywhere) are never listed or entered, unless you add a root inside one, such as your iCloud Drive folder under `~/Library`.
- A typed path is checked as typed before anything is looked up, then where it really leads, and only then whether it is a folder: a path into a hidden folder gets the same answer whether or not something is there.
- At most 2,000 entries are read from a folder, and 100 suggestions returned.

### Setting it up

Adding a project opens its setup. A project with no runs shows it on every page but Settings; one that is partway through shows it on the Overview (and at `#/setup`), and **Skip the rest** or, once its golden's test passes, **Go to the overview** finishes it. There are four steps, and each runs the command beside it in the project's folder, the same one you could type in a terminal:

| Step | Command |
|---|---|
| Inspect the folder: SDKs, the start command, and every tool with its effect. Tools that aren't wrapped are flagged with the code to wrap them | `shadowlap init` (the dashboard reads what [`init --json`](./cli.md#init) prints, from the job) |
| Record a first run | `shadowlap run -- <command>` |
| Make the replay clean | `shadowlap calibrate <run> --write` |
| Keep it as a test | `shadowlap pack <run> goldens/<name>`, then `shadowlap test goldens/<name>` |

Inspecting is done once `init` has run in the folder; a project recorded in a terminal first shows it as skipped, and can still be inspected. The job's drawer shows what `init` found, a line each. A Node the project pins before 18.18 (`.nvmrc` or `.node-version`) is flagged there: an agent on it never starts under Shadowlap, so **Record a run** stays off until the pin is raised and the folder checked again. A recording counts once it holds calls: one whose command didn't start (a typo), or whose agent stopped before its first model call, recorded nothing, and the step says so. When tools weren't wrapped while it was recorded, their calls aren't in it: wrap them, check again, and **Record again**. Until the replay is made clean, the newest recording is the setup's, so recording again in a terminal works too.

Making the replay clean replays the recording offline: when it replays clean as it is, the step is done by itself; when calibrate proposes normalizers for values the agent makes anew on every run, **Add it** writes them to `shadowlap.config.json`. The golden goes in a folder of its own, `goldens/<project>` unless you name another; Shadowlap never packs over a golden that is already there, and offers the next free name instead. **Pack as a golden** packs it and runs its test in one job, so leaving the page doesn't stop it halfway; the step is done once the test passes. A golden whose test failed keeps the step open with why and **Run the test again**; fix what changed (or record again), then run it. **Skip the rest** appears after the first recording, and finishing before the test passed counts the last step as skipped.

The same commands typed in a terminal move the setup on: `init` records what it finds, a recording counts once it holds calls, a clean replay of it (`shadowlap replay <run>`) completes step 3, and a pack of it under `goldens/` whose test passed (`shadowlap test`, which keeps each golden's result in the store) completes step 4; packed but not yet tested, the step offers **Run the test**. One step is current at a time: once a golden is packed, making the replay clean shows as passed by (it can still be run), and a test of the golden that passed counts as a clean replay too. `calibrate --write` in a terminal leaves nothing behind by itself; the setup's **Calibrate** then finds the replay clean as it is.

The browser never sends a command line, with one exception that already exists for a capture's replay: the command that starts your agent, which only ever goes after `--` in `shadowlap run -- <command>`. The server splits it into arguments without a shell, reading quotes as a terminal on macOS or Linux does, so the command the setup shows reads back as the same arguments: single quotes keep text as it is, and a backslash makes the next character text (`'it'\''s'`, `my\ file`). What only a shell would understand is refused rather than passed on as text: a pipe, `&&`, a redirection, `$VAR`, a leading `~`, a wildcard or a comment outside quotes, `$VAR` or a substitution inside double quotes, `$'…'`, and a backslash at the end of the line. So that a Windows path works, a backslash before a letter, a digit, `.`, `_` or `-` is kept (`C:\agents\run.py`), and two backslashes in a row are refused. Put the rest in a script. The first time a command runs in a folder, the dashboard asks before running it; the same command in the same folder doesn't ask again, unless its model calls would now go to another model server.

When `init` finds that the project talks to a model server of its own (`OPENAI_BASE_URL` in its `.env`, or a local base URL in its code, as with Ollama or vLLM), recording sets `SHADOWLAP_UPSTREAM_OPENAI` to that server, as `init` tells you to in a terminal, so the calls go there and not to the provider's API. A server address with credentials in it (a password, or a key in its query) is never stored or shown, so such a project is recorded in a terminal.

### Removing a project

**Remove from dashboard** takes the project off the list. Nothing on disk changes: the folder and its code, its store, `shadowlap.config.json` and the goldens stay, and the list remembers how far its setup got and the commands you confirmed, so adding the folder again undoes it. **Also delete its recordings** deletes the store as well (`.shadowlap/shadowlap.db` and the files SQLite keeps beside it) once you type the project's name, and the list forgets the project: added again, its setup starts afresh. It won't while a run is recording there (a run whose process is still there, however long ago it started; one a killed process left marked running doesn't hold it up) or when the folder can't be written to, and it never touches the goldens in your repository. Repair reports, exports and files sent to jobs, in `.shadowlap/repairs`, `.shadowlap/exports` and `.shadowlap/uploads`, are copies of their own and stay too: the dialog names the ones there, so delete them yourself if they hold what you mean to delete. With a [team store](./team.md), the dialog says how many of the runs are in it too, which stay there, and how many exist only here. The only project can't be removed.

## Send a run to someone

```sh
shadowlap export html <run> --lineage run.html
```

The same views as one HTML file, with the run's data built in and nothing to install or run: attach it to a pull request, keep it as a CI artifact, or send it to whoever asks what the agent did. It opens on the run that was shared, and holds Runs (the runs in the file) and, when it holds two or more, Compare between them; there is nothing to run from it and no search across runs, so `/` filters a run's calls. It holds recorded prompts and tool data, so the project's redaction rules apply by default; see [`export html`](./cli.md#export-html). **Share → HTML file** in a run's header writes the same file for that run and the runs it came from into `.shadowlap/exports/` and downloads it; its output says whether redaction rules applied. On a read-only dashboard it downloads the file without writing it. **Share → HAR** does the same for the model calls and names how many rules it applied.

## Security

Recordings hold prompts and tool data, so the dashboard is built to stay local:

- It listens on 127.0.0.1 only, and refuses requests whose `Host` is not localhost, so a web page on another name that resolves to your machine cannot read it.
- Every data request needs the session token that `shadowlap dashboard` generates at start and puts in the link's fragment (the part after `#`, which browsers never send to servers or in a Referer). Restarting the dashboard invalidates old links.
- Requests that change something are refused when they come from another origin, and when the page sending them shows another project than the current one (it says which in `x-shadowlap-project`).
- The browser never sends a command line: it names an action or a job and its fields, and the server builds the CLI arguments from the run, the call and those fields. The command you give a capture's replay, and the one a [project's](#projects) setup records, are placed only after `--`, split without a shell, and a project's asks before it first runs in a folder.
- A download is only a file a job reported writing, only from inside the project folder (checked again when you download it, links followed), and always saved rather than opened. Uploaded files stay inside the project folder and are deleted as described under Actions.
- A read-only dashboard refuses every request that would change something.
- The page loads nothing from the network (fonts are bundled) and runs under a Content-Security-Policy that allows only its own script.

To use it on a remote machine, forward the port over SSH (`ssh -L 4777:127.0.0.1:4777 host`) rather than binding it to a public interface. Closing the terminal stops the dashboard and its jobs; to keep it running after you log out, start it inside `tmux` or `screen`.

## How the page stays current

The server keeps a change feed: one small endpoint that says what changed since the page last asked, so a page that polls it fetches again only what moved. A run added, ended, labelled or deleted, by the dashboard, the CLI or another dashboard, means the run list; calls arriving mean the recording that is growing, with its count; a command's activity entry means the feed; a job starting, ending or reporting what it made means the jobs. A running job's output is not in the feed: the drawer follows it from the job itself, from the last line it has. The store counts its own writes, so asking costs almost nothing, even with a recording in progress. A run's page asks for the run again only when runs move or, while it records, when its own calls do: a finished run's page fetches nothing while another run records, and a recording's page fetches only the calls after those that won't change (`?after=`): from the first still on its way, or answered with a failure the agent may retry, which its retry answers again under the same number. Asked again, a run the page already has is answered 304 from where it stands (the rows of its family, its calls, its state, the fixes) without being worked out again, so another run starting or ending doesn't send it again. For a recording, the server reads and places in conversations only the calls that arrived since it last looked, so following a run of 50,000 calls costs what its newest calls cost; a call that feeds the model call after it waits for that call to arrive, and the run is worked out whole once it ends.

For contributors, the server's endpoints are registered by feature in `packages/dashboard/src/routes/`, and the shapes they answer with are in `packages/dashboard/src/views.ts` and `api.ts`. A read of something the store doesn't hold is a 404 with `{ error }`; the page asks its reads with `x-shadowlap-not-found: answer` and gets a 200 with `{ error, notFound: true }` instead, as it says what is missing itself and the browser would log the 404 as a failed load. The endpoints:

| Endpoint | |
|---|---|
| `GET /api/meta` | Version, store and its size, address, read-only and why, runs and attempts counted apart, live runs, job kinds, project folder |
