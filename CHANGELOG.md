# Changelog

Every notable change to Shadowlap is listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The release workflow lifts a version's section into its GitHub release notes, and publishes nothing for a version without one.

## [Unreleased]

The first release: record, replay and fork AI agent runs, find the call that lost a run, and prove a fix before it ships.

### Added

#### Record

- **`shadowlap demo`** shows the whole loop in about half a minute, with no key and nothing to clone: a refund agent recorded breaking its policy, replayed with 0 upstream requests, blamed to the model call that lost the run, and repaired, its fix proven and applied, against a scripted model on 127.0.0.1 that the demo says is scripted. It says how to read a probe and where its requests went, and `--keep <dir>` keeps its folder to open in the dashboard.
- **Model calls at the HTTP layer.** A sidecar on 127.0.0.1 records calls to Anthropic, OpenAI and OpenAI-compatible servers (Ollama, vLLM, OpenRouter, Groq) and Gemini, streaming responses byte for byte with their timing. `shadowlap run` points the official SDKs at it through their base-URL variables, so model calls need no code changes. Credentials are forwarded and never stored, and a model call's query string is kept, and matched, without the credentials in it.
- **Amazon Bedrock, Vertex AI and Azure OpenAI**, whose clients sign requests or fix their endpoint in code, are captured inside Node and Python agents and forwarded unchanged, signatures and HTTP/2 included, as are Claude on Microsoft Foundry and OpenAI's SDK on Bedrock. An AI SDK model named by a string (`'openai/gpt-5'`) is recorded on its way to Vercel's AI Gateway, where the AI SDK sends it. Any other host that speaks one of their formats, such as a gateway or a company's own proxy, is declared under `providers` in `shadowlap.config.json` and recorded as that format's calls.
- **What the agent saw is what is recorded.** An agent that leaves before its answer is whole ends the request upstream too, and is recorded as a disconnect its retry matches, which a replay holds for as long as the agent waited before cutting it; a stream the provider cuts part way breaks at the same place on replay; an unreachable or broken provider or host breaks the agent's connection as it would without Shadowlap (an HTTP/2 stream is reset), and a replay breaks it again; identical retries that race each other keep their own answers; and the sidecar's own answers are kept with their bytes and headers, so a replay sends the same. A request's numbers are kept as sent: an id past 2^53 keeps its digits through a replay, an override, a pack and Compare, and two ids that round alike stay two requests. A body is read whole or not at all, and one past its limit (1 GB for a model call) gets a 413. A Realtime WebSocket is tunnelled to its provider's hosts, unrecorded and named in the run's summary, and an SDK's own telemetry goes where the agent sent it and is never recorded.
- **Recording waits out a busy store.** A call's rows, and a run's start and end, wait their turn while another process holds the store, without holding up another run's stream, so no run is left marked as running; a run whose start can't be written whole, as on a full disk, leaves nothing behind; and `run`, `replay` and `test` say in their summary what of a run couldn't be written once it ended.
- **Tools, clock and randomness** through the TypeScript and Python SDKs. A tool declares its effect, `pure`, `read` or `write`; outside Shadowlap the wrapper is a passthrough, so it ships to production unchanged. A streaming tool replays every value it yielded and whether its caller stopped early, and a replay that reads on past that stop forks there. A replayed error is the one recorded: in Python an instance of the same builtin (`except KeyError` catches it) with its own plain attributes (an `OSError`'s `errno` and `filename`, openai's `status_code`), in Node with the fields JSON holds (a file system error's `errno`, `syscall` and `path`), and in both with the status of the response an HTTP client's error carries, never its headers, data or request. The Python SDK records coroutines, async generators and async callables under asyncio, trio and anyio, where a call cancelled while it waits on the sidecar never runs and never stays pending; it leaves `self` out of a method's arguments, is typed (`py.typed`, mypy `--strict`), brings a `shadowlap` command that runs the CLI at its own version, and its guard and capture are tested on Python 3.9 to 3.14. The Node SDK loads in an Edge runtime or a browser bundle, and ships a CommonJS copy for `require()`.
- **HTTP hosts as tools.** Hosts declared under `http` in `shadowlap.config.json`, such as a vector database or an internal API, are recorded as tool calls with an effect, from Node and Python.
- **MCP servers** behind `shadowlap mcp`, a proxy that records, replays and fences `tools/call`, with effects from the tools' annotations, for a server it starts or one it reaches over HTTP, and served to the client over stdio or, with `--listen`, over HTTP on a loopback address. A listener started on its own records each session into the run of the Shadowlap command that started its client, and refuses writes in a session it finds no run for; an answer a server over HTTP cuts off ends the call as an error, recorded so, never passed on as whole.
- **Framework adapters**, each tested against the real framework running its own agent loop: the Vercel AI SDK, OpenAI Agents SDK, Mastra, LangChain and LangGraph and the Anthropic tool runner in TypeScript; Pydantic AI, the OpenAI Agents SDK, LangChain, LangGraph, CrewAI, Google ADK, LlamaIndex, Microsoft Agent Framework, Strands, smolagents and Agno in Python; and the Claude Agent SDK in both, its built-in tools (Bash, Write, Edit and the rest) recorded and fenced through its hooks. The fence holds against other hooks: the query's own hooks run inside it, and a recorded write that a hook Claude Code reads from a file could rewrite (its settings, `.claude/settings.local.json` in the session's folder, at the repository's root and at a linked worktree's main checkout, managed drop-ins, a skill's or subagent's frontmatter, a local plugin) is refused on replay, naming the file, unless `disableAllHooks` turns that hook off as Claude Code resolves it; a session where another hook replaced the stand-in stops, saying so. A Claude Code or Claude Agent SDK recording replays in the next session and on another machine with no normalizer.
- **Scopes** for parts of an agent that run at once, so concurrent sub-agents keep their own recorded answers.
- **`shadowlap init`** finds a project's model SDKs, its framework (any of those above) and the models it names, its agent command and tools, suggests an effect for each tool, names a model sent to a host Shadowlap doesn't record with how to declare it, warns about a client that bypasses the sidecar and about a Node pinned before 18.18, and prints the steps to a first recording.
- **`shadowlap doctor`** checks Node and its SQLite, the guard preloads, Python, the store and the configuration, gives the fix for each problem it finds, and explains the newest run whose agent loaded no preload; a URL it shows carries no password or token.
- **The Node it needs, in one line.** The CLI runs on Node 22.16 or later, not 23, whose built-in SQLite has the full-text search every store uses; on another it says so before it loads. An agent on a Node before 18.18, which refuses the guard's preload, is named the same way, and no empty run is kept of it. When a launcher such as `npx node@18.17.0` picks that Node, `run` and `replay` can't ask it: they keep the empty run, and its summary says what Node's refusal above it means.

#### Replay and fork

- **A clean replay makes no upstream requests.** Calls match by what they ask, `(kind, fingerprint, occurrence)`, never by the order they arrive in, so parallel calls replay in any order; what a call asks includes the headers that change its answer, such as Bedrock's guardrail. A clock or random read matches only a recorded read of its name; a clock, random or pure read the recording never held is answered live and the replay goes on; and a replay of a 1,000-call run starts in well under a second.
- **A clean replay needs no real key.** An agent whose model client takes its key from the environment, as `new Anthropic()`, `new OpenAI()` and Google's clients do, replays without one: `shadowlap test`, the Action, recorded tests, `calibrate` and `bisect` give it a placeholder key for each provider whose credentials the environment lacks, and `shadowlap replay` for each whose key the recording's environment held, never in place of a credential you have, of any kind the provider's SDKs read (an AWS config file that names only a region, or an Azure CLI sign-in, is none). The sidecar refuses a live call that would carry one, with one line, so a placeholder never reaches a provider.
- **A fork at the first changed request**, with a structural diff against the closest recorded call and a normalizer hint when the change is a date or an id. After it, model calls and `read` tools run live and `write` tools are blocked or stubbed (`--writes`). What the recording left with the provider is rebuilt for a fork's live calls: a Responses run that continues a stored response sends the conversation in full, a call that names a Gemini or Vertex AI context cache the recording made sends the cache's contents, and one that names a file the recording uploaded sends the file's bytes, within the provider's limits. What can't be rebuilt is refused or named, with the reason: a stored conversation, a file the provider has deleted, a file or vector store a call names by its id alone.
- **A network guard** reports or refuses the connections and UDP sends that bypass Shadowlap (`--guard`), in Node and in Python, asyncio and uvloop included. Each process says when the guard loaded, so a run it never watched is named, and under `--guard block` fails, never called clean, saying it was not watched. The Claude Code CLI that the Claude Agent SDK runs loads no preload, so the fence names what that CLI can still reach, every query's in a process together: WebFetch, an MCP server over the network, a hook over HTTP, a command hook, stdio MCP server or credential helper that isn't Python, the claude.ai connectors, its OpenTelemetry export, the model API past Shadowlap, and its own nonessential traffic, which `withFence` turns off. With none of them left, `--guard block` passes the run; `guard.accept: ["claude-code"]` (or `SHADOWLAP_GUARD_ACCEPT`, or the Action's `guard-accept`) accepts that CLI alone and keeps block for Node and Python, and a value it can't take ends the command with 2 before anything starts.
- **Tools Shadowlap never recorded, named.** `run`, `replay` and `show` name each tool the model called, read from its own answers, that the run didn't record, with how often, what it does and how to have it recorded. Every command that replays a run (`test`, `replay` and `replay --repeat`, `blame`, `verify`, `repair`, `calibrate`, `bisect`, `injection`), and the recorded tests' plugins, refuses to run one that writes, or one nothing says the effect of, until it is wrapped, declared under `tools.unrecorded`, or allowed with `--allow-unrecorded`. A tool's verb counts where its name puts it, first or after `and`, `or` or `then` (`search_and_book` and `get_or_create_user` write, `get_merge_request` reads), a tool that runs SQL the model writes can write, and Claude Code's built-ins are told apart only in a run from Claude Code. An attempt that runs one anyway says so (`send_email ran for real, unrecorded`), in its JSON too.
- **Fewer false forks.** Dates and times near a run's start match across days, and `shadowlap calibrate` replays offline until clean, proposing a normalizer for each value the agent makes anew on every run.
- **What-ifs at call *k*:** `--override` a tool result, `--inject` an instruction, `--set` a request field, switch the `--model`, force a tool live (`--live-tool`) or a call (`--diverge-at`), apply a changed prompt from a later call (`--prompt-from`), and answer a model call with an HTTP failure (`--fail-at`), which sends nothing upstream.
- **`--repeat n`** runs a fork *n* times and shows the paths the attempts took; **`--watch`** replays again on every save.
- **The decision diff.** `shadowlap decisions` asks each recorded model call again with only a change swapped in (a model, a request field, or the system prompt and tools the working tree sends) and ranks what the model decides differently by consequence, a changed write first, with no tool run. Each step is asked several times under the change and as recorded, so a change ranks only when it shows beyond the model's own variation (`--samples`), and a step that got fewer than 3 answers either way is not ranked and settles nothing. `shadowlap migrate --to <model>` does it for a model a provider retires, verifies the runs whose writes change, reads a run with an unranked step as inconclusive, compares the cost per run and says what to set; the providers' retirement dates ship with their sources, and nothing calls home.
- **Partial recordings.** A run imported from a capture holds only model calls; a replay runs everything else live, with writes still fenced.

#### Fixes

- **`shadowlap blame`** finds the model call that lost a failed run: the last one whose answer, asked again, lets the run pass. It probes with forks that replay everything before the probed call, halving the run each time, and reports the call, or the calls it was lost between when no single one is pinned, a confidence read from the error bound of its probes, its 5% risk spread over them, and what the model answered there in the recording and in a fork that passed. A call the probes pin is checked against the next one with fresh pairs and named only when rescue drops there; otherwise the run was lost gradually, around the two, as `show`, repair and the dashboard's Fixes pages then say. In a terminal, blame, verify and repair fold their attempt lines, and blame's pairs, into lines that count them; `-v` keeps every line. `--scope`, `--model`, `--set`, `--budget` and `--json`.
- **`shadowlap verify`** accepts a change only when the failing runs it was written for are fixed, failing runs held out from it are fixed too, and no good run is 10 points or more worse than the same run under the code before the change, paired attempt for attempt, or than its golden's history, each session pooled by its first attempts under the same recording and checks, each decided at a stated risk. A good run's bound on its drop (`drop <= 0.10 (95%)`) rounds away from what it bounds. A replay that forks nowhere settles its run in one free attempt. It exits 0 when it accepts, 1 when it rejects and 3 when it can't decide, and reports each run's token and cost change.
- **`shadowlap repair`** blames the failing runs, asks a repairer you choose for rewrites of the system prompt or a tool description, and keeps the smallest rewrite verify accepts twice, the second time with fresh attempts, including on failing runs the repairer never saw, so however many candidates it tries, the chance it keeps one that falls short stays within the gate's risk. A repairer is any Claude model through the Anthropic SDK, any Chat Completions API, or your own Claude Code (`--repairer claude-code`, 2.1.248 or later), which runs restricted, with no tools, no MCP server, no session kept on disk and none of your user, project or local settings, so no hook, permission rule or plugin of yours meets what the failing runs held. A rewrite whose own words grow the input past `--max-growth` is rejected before verify spends anything, every repairer's answer is held to the 16,000 tokens the budget counts, the repairer is asked only while the budget left covers its most possible cost, else repair stops with exit status 3, and it is given up on after `--repairer-timeout`. Each candidate is verified in a temporary git worktree, with `--build` run in it on a `node_modules` of its own. The fix comes as a patch, a pull request body and a recording of each fixed run; `--apply`, `--branch` and `--pr` hand it over.
- **Fixes, kept.** A blame opens a fix, or joins one, by the run's labels, else its check, and verify and repair report to it; `shadowlap fix ls` and `fix show` say how far each step got, and `fix apply` hands a verified fix over: its patch into the working tree, the fixed runs copied in as goldens and tested, and the project's other goldens replayed offline to name each the patch makes diverge, without running one from a pack the repository doesn't track, those it left out named too.
- **Outcome checks** say what a passing run does (`--expect`, or `tests` in the config): tools that must or must not be called and with what arguments, call counts, token and cost budgets, and text in the output or the final answer.
- **Checks on order, conditions and earlier calls' values.** A `calls` rule says what every call of a tool comes after and what its arguments must be, against a value read from an earlier call (`"amount": {"<=": "@lookup_order.result.total"}`); a `when` rule applies checks once a call met a condition. Each check comes out passed, failed, inconclusive or not applicable, and a pass never rests on a value that was not there. `shadowlap check` tries a check on the recordings at no cost, and `doctor` names a misspelt tool or value.
- **Judge checks** ask a model a yes-or-no question about a run. The judge's call is recorded like any model call, so a golden is judged once when it is packed and every clean replay after is judged from the recording, free and the same every time; a fork asks the judge live, and its cost is reported apart from the agent's.
- **Gates with stated error rates.** verify decides each failing run, and blame each probe, by a sequential test between two pass rates as attempts come in, instead of a fixed count, and verify keeps a good run against its baseline by a test whose error holds at every look. Every verdict shows its tally and a bound that holds however its gate stopped (`passed · 12 of 12 · rate >= 0.73 (95%)`), and a good run its baseline's tally and a bound on its drop. An attempt the provider failed before the model answered anything is run again and never counted; one it cut short after is counted against either verdict, by a gate and a fixed count alike, so no verdict rests on how it would have ended, and an outage leaves a verdict inconclusive, never failed. A long run takes one more error in a row to stop for each tenfold of its attempts, so a flaky provider stops it no more often than a short one. Every risk a verdict line prints holds exactly at every look, and labels round a confidence down and a risk up.

#### Tests and CI

- **`shadowlap test`** replays committed recordings offline and fails on a divergence, a live call, a non-zero exit or a failed check, with JUnit, JSON and Markdown reports and pull request annotations. A recording marked `fork` may diverge and passes on its checks, repeated when a model varies.
- **Exit statuses a script can tell apart:** 0 when all is well, 1 when a check, gate or test failed, 2 for a command it can't run as given (and for `test` when the only goldens that failed are packs it needs `--yes` to run), 3 for a verdict that couldn't be reached (a blame not settled from the first model call, a repair its budget stopped), 70 for a bug in Shadowlap, `mcp` included, and 128 + n for a stop signal, also one that comes as a command finishes: 130 for Ctrl-C, and 129 for a closed terminal, which stops the demo, `replay --watch`, `serve`, `tasks serve`, `mcp` and `repair` as it stops a run.
- **A GitHub Action**, `devjoinedthechat/shadowlap`, that replays the recordings, puts the diff of each failure in the job summary and on the pull request, and keeps one comment on a pull request with each golden's verdict, edited in place and compared with the base branch's last session when the test history has one. It installs its own release of the CLI from npm without running an install script, and a build from source runs none either, in a home of its own, with none of the job's secrets.
- **Fix on failure.** With `fix-on-failure`, the Action blames a golden that fails a check, has a fix proposed and verified on the other goldens that fail the same check, those held out from the repairer among them, and on goldens that pass it, under the step's guard and with `fix-build` building the agent for each candidate, and opens a pull request whose checks start: with a `github-token`, or with the job's own token and a `workflow_dispatch` of the workflow on the fix's branch. The pull request says what the fix was verified on, and never claims checks it didn't see. A pull request from a fork is tested at its merge commit and gets no fix. The dashboard's Settings → CI writes the step with the permissions it needs.
- **Recorded tests** for your own suite: a pytest plugin (`@pytest.mark.shadowlap`) and `@shadowlap/test` for Vitest, Jest and node:test. A test records on its first run and replays offline after that.
- **Gated goldens.** A golden that may fork can be decided by a sequential test between two fixed pass rates (`good` and `bad`), which needs no history, or against its own test history, stopping as soon as the evidence is enough. A history baseline takes only sessions that passed on the default branch, and none a signal stopped, so a regression never becomes the standard it is judged by; past 40 attempts, a pass is held to the golden's record however the limit got there (`--max-attempts`, Run more attempts or a config `max`). `--inconclusive fail|warn` says what CI does when a gate, a check or an injection test can't decide. With neither given, a gate against history whose golden has fewer than 30 sessions only warns when it runs out of attempts, saying it needs more history (`warned` in the JSON report), unless the session's plan reads its last sessions below the ones before them, 99 to 1 likely or more, or a drop: then it counts, and says why (`counted`). The Markdown summary names what applied: the flag given, or the default and that rule. A clear failure fails either way. The Action can keep the test history between jobs, and its `inconclusive` input, empty by default, does as no flag does.
- **One risk for the whole suite.** `shadowlap test` splits one risk of a healthy suite going red for nothing, `--suite-risk`, 5% by default with the provider answering, across the gated goldens, sizes each gate's limit to fit, and says before it runs what the session will cost in attempts and dollars, which goldens can't keep within their share yet and by how much, and the plan's own chance of a red suite when its gates can't keep within the risk. A gate against history is planned over the pass rates its golden's last 30 sessions leave open, every attempt of them; the attempts it adds past its own limit pass only an agent its record backs, so a regression is caught as often as at that limit, and last sessions below the earlier ones beyond chance are named as a drop. The goldens' attempts run in turns, so a burst of failures lands on many goldens once each; errors in a row count across the session, which stops at 3 + ⌈log₁₀ goldens⌉ of them; and an attempt the provider cut short uses none of a gate's limit, up to as many again.
- **Injection tests.** `shadowlap injection` plants payloads in every read of a tool marked untrusted, each carrying a canary that occurs nowhere else, so a tool call carrying it proves the planted text caused it; `--clean` asks whether a recorded read caused a write. An attempt that obeyed keeps its proof when its provider fails after. A golden's `injection` gate fails CI while the agent obeys.
- **Error-path presets.** `shadowlap test --chaos` forks each golden where a tool times out or answers nothing, malformed or oversized JSON, or the provider answers 429 or 500, and judges each fork by the checks that hold on any path. A real provider error during a preset is the provider's: run again before the model answered, counted against either verdict after, and inconclusive when it stays down, its errors in a row counted across the session's presets.
- **Production coverage.** `shadowlap coverage` groups imported production runs by behaviour, names those no golden covers, and `--pack` makes a golden of one run of each.

#### Imports, exports and data

- **`shadowlap import har`, `nock`, `vcr` and `litellm`** turn a capture into a recording you replay your own code against; a LiteLLM gateway's production traffic becomes one run per correlation id.
- **Traces you already keep** become recordings: `shadowlap import otel` reads OTLP JSON with the OpenTelemetry GenAI or OpenInference conventions, and `langfuse`, `langsmith`, `phoenix` and `logfire` fetch a trace from Langfuse, LangSmith, Arize Phoenix or Pydantic Logfire with the keys in the environment, never storing them. Without a trace id, `langfuse`, `phoenix` and `logfire` bring every trace that started in a window (`--since 7d`, `--until`, `--limit`, `--trace-name`), one run per trace, and skip the traces imported before; Langfuse is read through its Observations API where the server has it. What the trace kept replays; the rest runs live, with writes fenced. The dashboard's Import dialog fetches from all four.
- **Exports:** `pack` (redaction rules applied, to a model call's path and the header parameters it is matched by too, such as a Bedrock model's or guardrail's ARN), `export html` (a run as one file with the dashboard's views), `export har`, `export otel` (GenAI semantic conventions) and `export dataset` (JSONL, OpenAI chat, Braintrust, Langfuse).
- **Recordings as data:** labels and notes that travel in packs, full-text search across prompts, responses and tool calls, and `shadowlap diff`, which starts with what changed between two runs. A label or note made while a run ends is kept with what the run wrote, and a store or a collector that can't write for a full disk says the disk is full.
- **`shadowlap rm` and `gc`** delete runs, old ones by age or count, and remove the recorded data nothing references any more.
- **JSON for scripts and coding agents** from `ls`, `show`, `search`, `diff`, `calibrate`, `label`, `blame`, `verify`, `repair` and `test`, and instructions to give Claude Code, Codex, Cursor and other coding agents.
- **The coding agents' instructions, packaged as skills.** `setup-agent` sets Shadowlap up for an agent (its tools' effects from their code, a first recording, a clean replay, goldens, the CI check), and `debug-agent` checks every change to the agent's prompt, tools, model or code against what it actually did, and debugs a failing run through to a verified fix. `shadowlap skill install` puts them into a project from the copy that ships with the CLI: as a Claude Code plugin in `.claude/skills/shadowlap/`; with `agents` (or `codex`, `cursor`, `copilot`, `gemini` and the other names) into `.agents/skills/`, where Codex, Cursor, GitHub Copilot, Gemini CLI, Windsurf, OpenCode, Cline, Amp, goose, Zed and Junie read skills; with `kiro` into `.kiro/skills/`. The repository is also its own Claude Code plugin marketplace, and CI runs every command the skills name against the reference agent and checks every installed copy with the Agent Skills reference validator.
- **The recording format, specified.** docs/recording-format.md, version 1: packs on disk and the recordings protocol over HTTP, with Shadowlap as the reference implementation.
- **A service the agent calls, recorded as a tool.** docs/downstream-services.md shows how a declared host's answers replay without the service.

#### Team store

- **Your team's runs in a bucket you own**, free and open source like the rest, with nothing to buy or add first. `shadowlap store set` names an Amazon S3, Cloudflare R2 or other S3-compatible bucket, a Cloud Storage bucket or an Azure Blob container in `shadowlap.config.json`, and every machine reaches it with its own credentials, found where the cloud's own tools keep them. Nothing is hosted, there are no accounts, and no cloud SDK is bundled.
- **`shadowlap push` and `pull`** send runs with their lineage, each blob once, and a run still recording when it ends, and bring teammates' runs back, checked as strictly as a pack. Labels and notes merge both ways, and every run says who made it, and in CI which CI. A pulled run reads as its author's recording, with the requests it sent and what it spent there (*≈$0.0030 spent · by maya*), and its replay asks before running the command it was recorded with.
- **`shadowlap test --push`** sends every test run and the session's report from CI; `shadowlap store ci` prints the step, with short-lived credentials wherever the CI and the cloud allow them, a checkout that keeps no token, and the provider keys its goldens that run live need, and `store push-from-ci off` turns it off for the whole team.
- **Pull requests stay in their own folder.** A pull request's CI job writes only under `pr/<number>/`, a pull leaves those folders out unless given `--include-pr`, and runs from one never go back into the team's. `shadowlap store policy` prints the two policies that make the cloud hold to it.
- **`shadowlap share`** writes a run's HTML report, with every redaction rule applied, to the bucket and prints a link that expires after 7 days.
- **`shadowlap store check`** proves this machine can list, write, read and delete in the store, and warns when versioning or an object lock is off; `store show` says what this machine knows, without a request.
- **A pulled fix runs nothing it carries.** Blame again, Run more attempts and Verify again build their arguments from the report and the flags kept beside it, each an allowed flag with a value of its shape. A pulled blame or verdict is marked pulled, runs without the teammate's `--build`, `--base` and command after `--`, spends at most twice what Shadowlap runs by itself, and runs only after a yes to the exact command line.

#### Dashboard and terminal UI

- **`shadowlap dashboard`**: runs and their forks, a strip of every call by origin, the calls, turns, context and cache use, timeline and family of a run, the conversation exactly as the model saw it at any call, streamed responses at their recorded pacing, fork diffs and Compare. Replay and every what-if but `--set` run from the page, and a run downloads as one redacted HTML file. `--port 0` takes any free port, and the link names it.
- **A run opens where it went wrong**: a fork where it forked, a run blame found lost at that call, a failed run at its first failing call, a recording at its newest; its calls grouped under the model call each belongs to and folded at will. Its page names the tools the model called that weren't recorded, a preload that never loaded or a process the guard can't watch (the Claude Code CLI the Claude Agent SDK runs), the WebSockets it opened and the reads it answered live; Provenance shows the gateway a call went through and the guard, and Tests explains a guard failure.
- **What a fork did differently**: the tool calls it made and didn't, its writes and what became of each (more than three grouped by tool and outcome, *send_email ×9 blocked, from #950*), and how each run ended, ranked as `shadowlap decisions` ranks a change.
- **Edit and fork.** Edit a tool's result, or what a person answered, from any tab of the call inspector and fork from it.
- **A good/bad key.** `+` and `-` label a run good or bad, its checkbox focused or not, the same key again takes it off, and `u` undoes a press. A good run is one a fix must not make worse than its own baseline, as `repair --keeps label:good` holds it. Runs heads the key *good · bad*, lists a label's runs exactly with `label:good` (`label:"needs review"` for a label with a space in it), and keeps its filters in the address, so a view can be shared and Back and Forward work.
- **Fixes shows the evidence.** A gate's attempts are grouped by what each did, and each verdict shows its bound, each good run its baseline and the bound on its drop as the CLI prints it (*drop <= 0.10 (95%)*), and a blame the calls it was lost between, or the two it was lost gradually around, as the Fixes list, Needs a look, the activity feed, Runs, a run's page, the Overview and the terminal UI say it too.
- **Large stores and long runs open at once.** Whatever reads every call of a run, or every run (a run's analysis, Provenance, Compare, a fix's page, Settings → Tools, the project switcher, Training, the search index), is worked out on threads beside the server: a request waiting behind a long one goes to a free thread, a third one answers behind two long requests, deletes run on a thread of their own, and runs written while the dashboard is open join its index in place, so every other request is answered meanwhile, and the Overview and Runs read at most 5,000 calls while you wait, leaving a longer run's totals to the warm-up. A long run's calls come a page at a time, any page at once, each read once however it is scrolled, and a page that can't be read is tried again after a growing pause; a recording opens at its newest call and follows it, read a page at a time as it grows; Runs and the sidebar list a long run before its totals are added up. Each page's code loads when it opens, and Runs reads only its first page again as runs change.
- **Compare shows a long pair's start at once:** the identical prefix and the first request that differs, kept with the `shadowlap diff` command when the rest takes longer than a request is given.
- **A store deleted while the dashboard serves it** is said to be, and one made in its place is read anew; a dashboard serving one store (`--read-only`, the terminal UI's) says the store was deleted or replaced, and asks to be started again.
- **Accessible.** The dashboard's text meets WCAG AA contrast in every state it shows, on a phone too, with targets of at least 24 px, a skip link, every scrolling pane reachable by keyboard, a focus order that follows the page, and focus that stays on the page when a link or a pick replaces what had it. A job's drawer tells a screen reader how the job stands, rather than every line it prints. CI checks it in Chromium with axe-core, at desktop and phone widths, over every page, run view, tab, menu and dialog of the whole demo.
- **`shadowlap ui`**: the run tree, a timeline with scopes, the inspector, playback (its speed on `<` and `>`), diffs, and a fork menu with every what-if but `--set`, in any terminal from 60×12, in the dashboard's colours on a dark or a light background, which it asks the terminal for (`SHADOWLAP_UI_THEME` chooses). It says how a run stands in the dashboard's words: the check it failed, where blame found it lost (marked in the call list, `b`), how its fix stands, and the tools it ran unrecorded, on a verdict tab (`v`) too. A fork shows where it forked and what changed there, on a diff tab beside the calls, then what it did differently from its parent, its writes and how each ended. Runs are named by what they were about, attempts fold into their run with how many passed (`a` lists them), and `+` and `-` label a run good or bad. Model calls are named by what they did, the conversation opens on what the call added, `z` widens the inspector, filters apply as you type, `s` searches what runs said and opens a match at its call, `N` notes a call, and help lists the keys of the screen you are on.
- **The Fixes flow from the terminal.** In the fork menu, `B` blames a failed run under the check it failed (its own, the config's or its fix's, else its exit), and `R` and `V` repair and verify the fix it fails in with the dashboard's own command, its repairer and its question about a run from someone else, built in the engine so both run the same line.
- **Cost, model and stop reason** for every call, from a price table the config can extend.

#### Security

- **Local only.** The sidecar and the dashboard listen on 127.0.0.1 behind a session token and check the host every request names, which blocks DNS rebinding; the dashboard checks Origin too, runs under a strict Content Security Policy, builds every command itself, answers an oversized request with a 413, and opens your browser without putting the token in any process's arguments.
- **No copy of a run carries a credential.** A model call's query string is kept without its credentials, every parameter named like one whatever its value (`key`, `token`, `sk`, `hash` and the rest), and its answer's headers are stored masked. A captured call's credentials are stored as `<CREDENTIAL>` wherever it sends them or gets them back: in its address (a webhook's secret in a Slack, Discord or Telegram bot address, in the call's name too; `session`, `sid`, `ticket` and `appsecret_proof` in its query, and `sk`, `ak` and `hash` when their value reads as one), in its body, and in its answer's headers (one whose name reads as a credential or holds a token, secret, password or credential word, a page's token aside; `*-authorization`, `*-auth` and `*-session` headers; a JWT after its scheme; the token in a URL that a `location`, `content-location`, `link`, `refresh` or htmx header names; a `www-authenticate` challenge), each masked in place; its request's headers are never stored. Every copy of a run (a pack, an HTML report, a share link, a HAR, a trace, a dataset, a push) also masks a key its command line carries (`--api-key …`, `KEY=…`, a header line, a URL's password).
- **Credentials are masked by a body's shape, not its content type.** A captured body is read as JSON (also sent as text or untyped, behind a byte-order mark or an XSSI prefix, in a JSONP call, or among other text), lines of JSON, an event stream (each event's `data:` lines joined), XML or HTML (an element named by a `name` or `key` attribute too), a form, multipart parts, a GraphQL query, or `key: value` lines (YAML, INI, .env), and masked inside its strings too: JSON in a string, a URL's query, session and password, a connection string, a JWT under any name or in a sentence, and the password of any URL a text holds. An answer's body is read the same way, a token response's `access_token` and `refresh_token` among what it masks, and a body masking can't read still goes through, stored as `<CREDENTIAL>` whole. Every pattern masking reads a body with passes the check a redaction rule's must, and a body of 64 KB or more is masked and stored on a thread of its own, off the one every model call goes through. SECURITY.md says what masking doesn't read, which a redaction rule covers.
- **Credentials stay on their origin.** A redirect a captured `fetch` follows to another origin goes without the agent's `authorization`, `cookie` and `proxy-authorization`, as `fetch` itself does, and a loop of redirects ends at the twentieth; the headers capture adds for the sidecar never follow a redirect to another host, in Node or Python; and a model API's redirect is never passed on or replayed.
- **Packs and captures are untrusted input:** validated before anything is written, hash-checked, refused on symbolic links and oversized files, each file read on the descriptor it was checked on, credentials dropped. A pack's redaction rules are checked before they run.
- **Someone else's command runs only after a yes to it.** `test`, `bisect`, `injection`, `decisions` (`--from-code`, `--then-verify`, `--verify`), `migrate`, `tasks score` and `tasks serve` run a golden recorded here, or one the repository tracks, as it is; any other, a pack that reuses the id of a run recorded here with a command of its own among them, asks at a terminal, runs with `--yes`, and isn't run without a terminal. A replay of an imported or pulled run, or of one a program started through the sidecar's API with a command of its own, asks the same. The question shows the exact command line, a format character or line separator escaped (a pulled record holding one is refused), and the dashboard's or the terminal UI's yes covers only the lines it showed, whatever the action asked first: one error-path preset's yes runs no other.
- **A capture's message is only ever an argument of your agent's.** `coverage --pack` refuses a command where `{message}` would run as code or name what runs (through a runner such as `npx`, `npm exec`, `uv run` or `cross-env` too), checks a `{message:/regex/}` as a rule's pattern, leaves out a capture whose message would start an argument with a dash, and on Windows escapes twice the arguments of a batch file that reads them again, such as `npx.cmd`.
- **No pattern stalls a replay.** One that could take too long is refused wherever a rule is written or read, a divergence hint's suggested normalizer included: a backreference, a repeat the next character doesn't settle inside another, two such repeats outside one, or more than 10,000 characters. The rules a document meets run within 5 seconds and are stopped past it, naming them, and a replay answers that call with why and goes on.
- **A repair rewrites only prompt text, and only in a copy.** A rewrite keeps exactly the placeholders of the text it replaces and adds none, nor a quote or backslash. Each candidate is tried in a temporary git worktree, never in your working tree, with at most 256 MB of untracked files copied in; a prompt file is never read or written through a link out of the repository, nor through a hard link; and no candidate touches a recording (a pack's `run.json`, calls or blobs, `__recordings__`) or Shadowlap's config (`shadowlap.config.json`, `.shadowlap`), each name read as Windows reads it too, which a pull keeps out and `fix apply` and `repair` refuse.
- **The Action keeps the job's tokens from the agent.** No GitHub token the job holds (`GH_TOKEN`, `GITHUB_TOKEN`, `github-token`, the OIDC request token, or a copy) reaches the CLI or the agent. A fix's branch is pushed with the token in git's environment alone, from a repository of its own with no config or hooks, to the repository the runner names and nowhere else, and its pull request is opened through GitHub's API; the workflows Shadowlap writes check out with `persist-credentials: false` and name no `GH_TOKEN`. The Action edits only a comment by the account its token posts as, and refuses `pull_request_target`, `workflow_run` and `issue_comment`. What a run, a model or GitHub wrote shows as text in a fix's pull request body, the comment and job summaries, where no image, link, mention, issue reference, math or emoji renders from it, and never starts a workflow command in the job's log, `shadowlap test`'s own lines included.
- **Signed reasoning stays as recorded in a pack**, so a fork's provider accepts it, and `pack` names each redaction rule that matches inside it; a copy that is only read masks it.
- **The team store's folder is all a pull reaches.** It reads only objects named as a push names them, never a key with a `.` or `..` part.
- **Recorded text is escaped** wherever a terminal shows it.
- **A store is its owner's alone.** It is readable only by its owner and opened only as a regular file of theirs, never through a symbolic link, in a directory only they can write to that no other user's open folder holds; one a newer Shadowlap wrote is refused.
- **Telemetry is off:** nothing is sent unless `SHADOWLAP_TELEMETRY_URL` names a collector you run. The collector is in the repository, installs nothing but Shadowlap's engine, and refuses any time before 2025 or more than a day ahead of its own clock.

#### Built on

- **Open protocols:** the SDK wire protocol and the recording format are specified, with a conformance suite of fourteen scenarios that needs no API keys. The engine is documented as a library.
- **Few runtime dependencies, held by a test.** The engine, sidecar, SDKs and adapters install nothing else. Nor does the dashboard; the CLI adds commander, and the terminal UI, which the CLI uses, adds Ink and React.
- **Light to install.** Every package together is 4.1 MB to download and 16 MB installed. Source maps name each file's TypeScript without carrying it, except in the SDKs, the adapters and @shadowlap/test, which ship their source; their CommonJS copies are type-checked as CommonJS and mapped too. The `shadowlap` package exports its module and `package.json` only; its command is the `bin` the manifest names.
