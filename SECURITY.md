# Security

Shadowlap sits between your agent and your model provider, stores what passes through, and replays it by running commands. Please report vulnerabilities privately.

## Reporting

Use GitHub's private vulnerability reporting on this repository ("Security" → "Report a vulnerability"). You'll get an acknowledgement within 3 days and a fix or a plan within 14. Please don't open public issues for security problems.

## What's in scope

- The sidecar: request handling, the loopback binding and session token, credential handling, replay serving.
- The store and the pack format: what is written to disk and how packs are parsed. Packs are untrusted input.
- The dashboard server and the terminal UI, including the actions they run.
- `shadowlap mcp`, how it finds a running sidecar, and what it serves with `--listen`.
- The SDKs and the telemetry client and collector.
- The team store: how `push`, `pull`, `share` and the store commands reach a bucket, use credentials and check what they read.
- The GitHub Action: what it installs, the tokens it is given, and the fixes and pull requests it opens.

## What Shadowlap does

### Recording

- The sidecar binds to `127.0.0.1` on a random port and requires a per-session token in every URL. It answers only requests that name it in `Host` by a loopback address, or that in-process capture redirected to it, which keep the host they were for and name that host, one Shadowlap captures, in `x-shadowlap-upstream`; this blocks DNS rebinding, as the dashboard's check does.
- Credentials (`x-api-key`, `api-key`, `authorization`, cookies, and AWS's `x-amz-security-token`, `x-amz-date` and `x-amz-content-sha256`) are forwarded upstream but never stored, in whichever of them a client sends its key (anthropic for Python 2.0 and later sends it as a bearer token), and an offline replay needs no real credentials. A model call's query string is stored without the credentials in it (`key`, `api-key`, `subscription-key`, a signature, and the other names [docs/normalizers-and-redaction.md](docs/normalizers-and-redaction.md#redaction) lists), and the `anthropic-organization-id` an answer names is not stored either. The headers of a model call's answer reach the agent unmasked, less a `location`, the hop-by-hop headers and the provider's own credential headers, and are stored with each credential they carry masked, as a captured host's are: a token header, one whose value is a JWT (a gateway's `x-amzn-oidc-data`), a token in a URL in `link` or `content-location`, a challenge's token.
- Node and Python agents get a preloaded capture module that sends to the sidecar the calls to known model hosts (Azure OpenAI, Vertex AI, Bedrock, Claude on Microsoft Foundry, and the three base-URL providers) and to the hosts that `providers` in `shadowlap.config.json` declares, naming the original host in `x-shadowlap-upstream`. The sidecar forwards such a call only to an `https` origin matching that provider's host list (for a declared host with a port, that port over `http` too), and answers anything else with 403, so it can't be used to relay requests to arbitrary hosts. A signed request is forwarded unchanged unless an intervention changes it; then it is signed again with the credentials the agent signed with, when Shadowlap can read them from the environment or the shared files, and otherwise refused with the reason. When the Node module follows a redirect for `fetch`, a request sent on to another origin goes without its `authorization`, `cookie` and `proxy-authorization`, as `fetch` itself drops them. The headers the module adds for the sidecar alone (`x-shadowlap-upstream`, `x-shadowlap-scope`, `x-shadowlap-failures`) never go anywhere else: a redirect a captured call's answer gives to another host, whether the Node module follows it or Python's httpx or requests does, which copy a request's headers onto it, is sent without them. `SHADOWLAP_CAPTURE=off` turns the module off.
- HTTP hosts declared under `http` in `shadowlap.config.json` are captured the same way and recorded as tool calls. The sidecar makes those calls itself only to a host the config declares, over `http` or `https`, and answers anything else with 403. Their request headers are never stored. The credentials in their address are stored as `<CREDENTIAL>`, in the call's name too: a webhook's secret in its path (Slack's `/services/T…/B…/<secret>` and its workflow and trigger addresses, Discord's `/api/webhooks/<id>/<token>`, a Telegram bot's `/bot<id>:<token>/`), a path's session, and its query's (`session`, `sid`, `ticket` and `appsecret_proof` there, beside the names a body's credentials go by). So are those in their body, read by its shape whatever its content type says: a form; JSON, also sent as text or with no type, behind a byte-order mark or an anti-XSSI prefix, or in a JSONP call (each member whose name reads as a credential, such as `api_key`, `password` or `client_secret`, or has a password or secret word anywhere in it, such as `SecretString`, at any depth; one whose last words name or describe the secret, such as `secret_name`, `SecretArn` or `password_policy`, keeps its value, but an id such as `secret_id`, a hint or a URL never does), and the JSON objects among other text (after a comment, before a `;`, run together, in a page's script such as `__NEXT_DATA__`); lines of JSON, a line that isn't JSON among them left as it is; a multipart body's fields and parts; an event stream's data, each event's `data:` lines read joined as a client reads them; XML and HTML elements and attributes, an element named by its `name` or `key` attribute as by its tag (`<entry key="db.password">`, `<input name="SAMLResponse" value="…">`, a SAML attribute's values); `key: value` and `key = value` lines (YAML, an INI file, a .env file); a GraphQL query's inline arguments, block strings too; and a body that isn't UTF-8, read byte for byte. Inside a body, every string under a credential member, a JWT whatever its name or wherever it stands in a text (after `Bearer `, in a sentence), and the credentials in a string are masked too: JSON in it, a URL (its query, a path's session, its password), a query string, a connection string, and the password of any URL a text holds, wherever it stands (`DATABASE_URL=postgres://app:…@db` in a .env file, a URL in a sentence or a log line). So are those a response hands back, in its body read the same way (an OAuth token response's `access_token` and `refresh_token`, an STS answer's `SecretAccessKey` and `SessionToken`) and in its headers: a header's whole value (`authorization`, `proxy-authorization`, any `*-authorization` or `*-auth`, OpenStack's `x-subject-token`, Swift's `x-auth-token`, GitLab's `private-token`, `x-access-token`, AWS's `x-amzn-oidc-data`, any whose value is a JWT, alone or after its scheme, any whose name reads as a credential, or any with a token, secret, password or credential word anywhere in its name, such as `x-session-token-raw`, but a page's token; a count or a limit of tokens, such as Bedrock's `x-amzn-bedrock-input-token-count`, and Azure's `azureml-model-session`, a routing hint that signs nobody in, are kept as sent unless their value reads as a key), and the credentials in a URL a header names (a redirect's `location`, `content-location`, `x-original-url`, `x-original-uri`, `x-forwarded-uri`, htmx's `hx-redirect`, `hx-location`, `hx-push-url` and `hx-replace-url`, a `link`, a `refresh`: the code or token in its query, fragment or a URL inside it, a path's session, a password or a token given as its name) and in a `www-authenticate` challenge. Each is masked in place, the rest of the body kept as the service sent it. The agent gets the real values while recording, and a client that reads its token from the response still finds it there on replay. A response's `set-cookie` is never stored. Masking reads what a credential is written as, not what it is encoded into: a secret left encoded is stored as it came, in base64 (JSON a form field carries, a JWE), percent-encoded twice, in a string nested more than six deep (an event stream inside an event's data is one level), or in UTF-16; and a body stored compressed as it came: a request body the agent compressed, and an answer under two content encodings at once (`gzip, br`), which the sidecar passes on as it came, without its `content-encoding`. Write a [redaction rule](docs/normalizers-and-redaction.md) for a secret left encoded: every copy applies the rules. No rule reads a body stored as bytes (compressed, UTF-16), and a push applies none, so keep a key out of those.
- Masking a captured body reads all of it, in time that grows with its length, never its square: each pattern it reads a body with passes the check a redaction rule's pattern must, and a test holds them to it. Counted in CPU time, which a busy machine inflates far less than the clock, a megabyte took 20 to 40 ms for JSON, a page or a binary body, 50 to 80 for an event stream or lines of JSON, and over 400 for text shaped to be slow (an object opened over and over, never closed), so storing a 20 MB body held the sidecar's thread, which every agent's model streams and calls go through, for 0.4 to 1.5 seconds, and over 8 for one shaped to be slow. A body of 64 KB or more is masked and stored on a thread of its own, and the sidecar's thread only hands it over and takes it back stored: under 10 ms for 20 MB, about 95 for a 20 MB JSON request, whose stored body comes back as values. A shorter one is stored in place, in 25 ms at most. What is stored is the same either way, and the call is answered once it is.
- A replay can give the agent a placeholder key (`shadowlap-offline-replay-placeholder`, or AWS credentials whose access key is `SHADOWLAPREPLAY` for Bedrock), so a client that takes its key from the environment sends what the recording answers. It gets one only for a provider the recording called whose credentials the environment lacks, counting every source the provider's SDKs read: a key or token variable set and not empty, an Anthropic profile (`ANTHROPIC_PROFILE`, `ANTHROPIC_FEDERATION_RULE_ID`, or an active profile in `ANTHROPIC_CONFIG_DIR`, `$XDG_CONFIG_HOME/anthropic` or `~/.config/anthropic`), `OPENAI_ADMIN_KEY`, Microsoft Entra ID (`AZURE_OPENAI_AD_TOKEN`, `AZURE_CLIENT_ID`, `AZURE_FEDERATED_TOKEN_FILE`, `IDENTITY_ENDPOINT`, `MSI_ENDPOINT`), and AWS's profile, web identity, container credentials, `AWS_BEARER_TOKEN_BEDROCK` and a profile in its shared files that holds credentials. An Azure CLI sign-in is none, since Azure OpenAI's and Foundry's clients read it only through a token provider their code gives them, and so is an AWS config file that names only a region. A key you set is never replaced. Offline replays get them (`shadowlap test` and the GitHub Action, recorded tests, `bisect` without `--fork`, `calibrate`); `shadowlap replay`, which goes live from a fork, only for a provider whose key the recording's own environment held, so a key from a `.env` file, a token provider or an instance role is left to the agent; Azure OpenAI only for a recording whose environment held `AZURE_OPENAI_API_KEY`; Azure OpenAI and Bedrock none with `SHADOWLAP_CAPTURE=off`, when their calls would go straight to the provider; commands that run live on purpose none. [docs/how-it-works.md](docs/how-it-works.md#keys) lists which commands are offline and which may go live.
- A placeholder is never sent. The sidecar answers a live call that carries one, in any header, in an AWS signature or in the query string, with `a live call needs a real key: set ANTHROPIC_API_KEY, or keep the replay offline` instead of forwarding it, whatever the upstream: a provider, a gateway, a model server on this machine or a mock; so is a call to a host declared under `http` that passes one on. A run keeps the names of the key variables its environment held (`keyEnv`), never a value, and a reader of a pack takes from it only the providers and variables Shadowlap knows.
- A model API's answer reaches the agent without a `location` header, live or replayed: no model API redirects, and a client that follows one (Node's `fetch` does) sends every header again, its key among them, to wherever it points.
- A WebSocket under a provider's path, such as OpenAI's Realtime API, is tunnelled only to the hosts that provider's calls may go to, and nothing sent over it is recorded; an offline replay refuses it. An SDK's own telemetry (the OpenAI Agents SDK's trace export) is passed on while recording, to the host the agent sent it to when that host is its provider's, else where the provider's calls go, and never recorded; a replay answers it itself, so a replay's traces never reach the provider.
- A request's body is read whole or not at all: one past its limit (1 GB for a model call) is answered 413 with none of it kept, and nothing is done with part of a message whose client left. The dashboard and the telemetry collector read theirs the same way.
- Recordings live in `./.shadowlap/`, which gets its own `.gitignore` so they stay out of version control. A new store directory is readable only by you (`0700`), and the database and its WAL files are `0600`. A store created by an earlier version is tightened when it is next opened. A store is opened only when its file, and its write-ahead log and shared-memory files when they exist, are regular files you own, in a directory you own that no one else can write to: a symbolic link there (which a checkout could plant), a folder or another user's file is refused, and so is a store directory that is a link, another user's, or writable by its group or by everyone (a shared `/tmp` among them, where anyone could put a link where a store's files go), or one in a directory another user keeps that everyone can change and that isn't sticky (where anyone could put another directory in its place), before anything is written in it. A new store is made with `O_CREAT | O_EXCL | O_NOFOLLOW`, never through a link.
- `.shadowlap/active.json`, which tells `shadowlap mcp` where the running sidecar is, carries the session token. It is written `0600`, and a symbolic link at that path is replaced rather than followed.

### Packs

A pack can come from anyone: a colleague, an issue attachment, a pull request. `shadowlap unpack` and `shadowlap test` treat it as hostile until checked.

- **Validation before any write.** Every run and call is checked for type, range and shape. Ids must be real run ids and blob hashes, so nothing in a pack can become a path. Strings in ids, names and command lines may not contain control characters, except that a command line and its folder may hold tabs and line breaks (`python -c '…'`), which every terminal shows escaped; nor may a command line hold a format character (a right-to-left override, a zero-width space) or a line or paragraph separator, which would disguise the command a replay asks to run. A time more than a day ahead of this machine's clock is refused, and a run marked as still running comes in as interrupted, so a pack can't hold up `rm` and `gc` with a recording nobody makes. Errors name the file and line.
- **Rules are checked before they run.** A pack's redaction rules, and the normalizer a divergence hint suggests, are read as the config's are, since a replay applies the rules to every request and the terminal UI and the dashboard offer to add the normalizer: a pattern that could take too long (a backreference, a repeated part whose end the next character doesn't settle inside another, two of them outside one, more than 10,000 characters) is refused, each path is parsed, and no name, path or replacement may hold control characters, before anything is imported. A pattern the check takes can still take the square of a long text (`.*x`), so the rules applied to any one document run within 5 seconds and are stopped past it, naming them: a replay of a pack whose rule runs that long answers that call with why, and goes on.
- **Integrity.** Every blob is verified against its SHA-256 name (one git checked out with its line endings converted to CRLF is verified with them converted back, and imported only if that matches), and every blob a call references must be present, including each part of a chunked request. A pack that fails any check imports nothing.
- **Files.** Only regular files are read. Symbolic links, unexpected files in `blobs/` and oversized files are refused. Each file is opened without following a link and checked on the descriptor it is read from, so a link or anything else swapped in after a check is never read, and a file that grows or shrinks while it is read is refused. Limits: 256 MiB per blob, 4 GiB of blobs, 16 MiB for `run.json`.
- **Imported commands need consent.** A pack records the command that produced it, and replaying re-runs that command. Imported runs are marked, whatever the pack claims about itself. `shadowlap unpack` prints each imported command. `shadowlap replay` of an imported run asks before running it, refuses without a terminal unless you pass `--yes`, and runs your own command without asking when one follows `--`; so does `shadowlap bisect` of one, which would run it at every commit it tries. Replays of an imported run inherit the mark. A run a program starts through the sidecar's API with a command of its choosing (`POST /v1/runs`, or the recordings API's `command`) is marked the same way, since whoever holds the session token, an agent the sidecar records among them, chose it. The terminal UI and the dashboard show the exact command line, and ask a yes of its own before a replay of an imported run, after whatever the action asked first.
- **A golden's command from a pack you didn't make or add needs a yes.** A golden's replay runs the command its pack recorded, and so does every command that replays a golden: `shadowlap test` (with `--chaos` too), `bisect`, `injection`, `decisions` (with `--from-code`, `--then-verify` or `--verify`), `migrate`, `tasks score` and `tasks serve`. One this machine recorded, with the command it was recorded with, or one whose pack your git repository tracks (its `run.json` is in the repository's index), runs without asking: that is where your goldens live, and in CI a pull request that changes a golden could change any other code CI runs too, so review changes to goldens like changes to code. A pack from anyone else, outside the repository or in it but not added, runs its command only after a yes at a terminal or with `--yes`; a pack that reuses the id of a run recorded here, with a command of its own, is someone else's too. Without a terminal, as in CI, that golden isn't run, saying why; `tasks serve` asks as it starts, and serves only the goldens you said yes to. The dashboard asks the same question, naming the command, before a job that passes `--yes` on (decisions, migrate, verifying what a session flagged, an injection test), and passes `--yes` only once it asked; its other jobs run the CLI with no terminal, which refuses such a golden.

### Captures

`shadowlap import` reads a capture made by something else — a HAR, a nock recording, a VCR cassette
— and a capture can come from anywhere a pack can. It is treated the same way.

- **Nothing identifying is taken from the file.** Run ids, call numbers, fingerprints and occurrences are computed, never read from the capture, so nothing in it can become a path or collide with an existing run.
- **Credentials are dropped**, not stored: `authorization`, `x-api-key`, `api-key`, cookies, `proxy-authorization`, `x-goog-api-key` and `x-amz-security-token`, on both the request and the response, and the credentials in a URL's query string. The rest of an answer's headers are kept as the capture holds them, and every copy masks a credential among them.
- **Header text is escaped and bounded.** Header names and values end up in run metadata that terminals and the dashboard render, so control characters are escaped where they are stored rather than relied on to be escaped at every point of display. Names are capped at 256 characters, values at 8192, and a call keeps at most 100 headers. Real HTTP headers carry neither control characters nor those lengths, so nothing legitimate changes — including a fingerprint.
- **Only model API calls are imported.** An entry whose host is not one of the six providers is skipped with a reason, so a capture of a whole browsing session contributes only its model traffic.
- **No YAML parser is trusted with a cassette.** `import vcr` reads VCR's JSON serialization; a YAML cassette has to be converted first, deliberately.
- **An imported run carries no command.** A capture says what was sent, not what sent it, so there is nothing to execute: the run is marked imported and its recorded command is the non-runnable placeholder `<no-recorded-command>`. Replaying it needs a command you supply after `--`; `shadowlap replay` without one, and `shadowlap test` on a golden packed from it, refuse rather than run the placeholder.
- **A capture's message is only ever an argument of your agent's.** `shadowlap coverage --pack` fills `{message}` in the command you give with a capture's first message, text from production. A placeholder where the message would run as code or name what runs (a shell's script, the argument after an interpreter's `-c`, `-e` or `-m`, the program, the script an interpreter runs or one of its flags, the command a runner such as `env`, `cross-env` or `npx` runs, or what a package manager's subcommand such as `npm exec`, `pnpm dlx`, `bun x`, `uv run` or `pipx run` runs) is refused, and a capture whose message would start an argument with a dash is left out. A `{message:/regex/}` pattern is checked as a redaction rule's pattern is, and runs on each message within the same time limit. On Windows, a batch file that reads its arguments again, passing them on with `%*` as npm's `npm.cmd` and `npx.cmd` and every bin npm, pnpm or yarn installs do, or putting one in its line as `%1` or `%~1`, has cmd.exe read them twice, so they are escaped twice: a quote in the message can't end it there, nor `%~1` take its quotes off, and run what follows as a command. Only a file that reads its argument as `"%~1"` alone, which is safe escaped once, gets it escaped once. A batch file that passes the argument on to another batch file has cmd.exe read it a third time, which no escaping can foresee: give `coverage --pack` a command that runs your agent, not a chain of batch files.
- **Imports are partial recordings.** A capture never saw tool, clock or randomness calls, so a replay runs those live. Write tools are still fenced by `--writes`, which defaults to blocking them.

### Output

Recorded strings are shown with control characters, format characters (a right-to-left override, a zero-width space) and line and paragraph separators escaped, in the CLI, `diff`, reports and the terminal UI, so a recorded prompt, tool name or error cannot rewrite your terminal or disguise what it shows. A command line you are asked to say yes to shows a word holding such a character in `$'…'` quotes, the character as its escape, so it shows what runs and still runs when typed.

### Dashboard

- `shadowlap dashboard` listens on `127.0.0.1` only and answers only requests addressed to `localhost` or a loopback address, which blocks DNS rebinding.
- The link it prints carries a random session token in the URL fragment, so the token never appears in server logs or `Referer` headers. Every API request must send it. The dashboard opens your browser through a file only you can read, in a folder only you can open, which sends it on to the link, so the token is never in a process's arguments, where any user of the machine could read it.
- Requests that change anything are refused when a browser sends them from another origin, even with the token.
- The page runs under a strict Content Security Policy, loads nothing from the network, and serves only its own bundled files.
- Actions map to a fixed list of CLI commands built on the server. The browser never sends a command line. A job that would run someone else's command (a pack's, a teammate's pulled from the team store, one a program sent the sidecar) is refused with a question naming the exact command lines, and its `confirm`, a digest of those lines; the yes the page sends back is that digest, so it says yes to those lines only. The server builds the command again for the yes, and one that now differs, because a pull changed the fields it is made from, is asked again. An answer edited in the call inspector (**Edit and fork**) goes to the server as an upload, is checked as untrusted data (UTF-8 text: for a tool's result JSON of at most 2 MB, for a person's answer at most 65,536 characters), and becomes the fork's `--override`, which the server writes into the command itself.
- What reads a whole run or the whole store (the Overview, a run's page, Compare, the Runs table's totals) is worked out on threads beside the server, each through a connection to the store that only reads.
- A run imported from a capture has no command, so its replay asks for yours. What you type is split on the server and placed only after `--`, where `shadowlap replay` takes the agent's command; it never becomes one of Shadowlap's own arguments. It is your command, so it runs without the consent an imported pack's command needs.
- **Share → HTML file** saves a run and the runs it came from as one HTML file, with the redaction rules in `shadowlap.config.json` applied, as `shadowlap export html --lineage` does. With no rules, the Share menu says a copy holds what was recorded.

### Team store

The team store is a bucket you own. Shadowlap hosts nothing for it, and nothing calls home.

- **Credentials stay on each machine.** Every machine reaches the bucket with its own credentials, found where the cloud's own tools keep them; `shadowlap.config.json` names only the bucket. Google and Azure credentials, whose signatures don't name the host, are sent only to the cloud's own addresses over https or to this machine, and an `?endpoint=` anywhere else is refused, so a committed config can't send them somewhere else.
- **Runs go up as recorded, but without their credentials.** A push applies no redaction rules: the bucket holds what `.shadowlap/` holds, so give it the same care. A credential a recording made by an earlier version kept stays behind: a model call's query string goes without its credentials, a credential response header with `<CREDENTIAL>` for its value, and a captured call's name, address, request and answer with their credentials masked, as the sidecar records them. A key the agent's command line carries goes as `<CREDENTIAL>` too, as in a pack, an HTML report, a trace and a dataset: the value of a flag that takes one (`--api-key …`, `--token=…`, `-password …`, but not `--token-file …`), an assignment, to the end of the argument it is in (`OPENAI_API_KEY=…` after `env`, `--set auth.password=…`), a header line (`-H 'Authorization: …'`), a JWT given as an argument of its own, and a URL's password, query credentials and webhook secret; and each of them in a script a shell runs (`sh -c 'OPENAI_API_KEY=… node agent.js'`, `bash -lc '…'`), read word by word as the shell reads it: an assignment's value to the end of its word, the rest of the script kept. A fix goes up with the command line each of its blames, verdicts and repairs ran, and the flags kept beside them to run each again, a command after `--` and a `--build` included, with the same credentials masked; this machine keeps those command lines masked too, and the flags as they ran, which run them again here. The store keeps a run's command as it ran, which a replay runs again; whoever replays a copy gives their own key. A share link's report has every redaction rule applied, holds no credential a recording kept, and masks a model's signed reasoning like any other text; the link expires after 7 days.
- **Only the store's folder is reached.** Anyone who can write to the folder names the objects in it, so a pull reads only objects named as a push names them (a run's id and a blob's hash are checked before they make a name), and no request is ever made for a key with a `.` or `..` part: nothing outside the store's folder is read or written with your credentials.
- **Pulled runs are untrusted input**, checked as strictly as a pack: every record validated, every blob checked against its hash, every redaction rule's pattern read as a pack's is, nothing in them that could rewrite a terminal. A pulled run is marked imported, so replaying its command asks first. A run that fails the checks is skipped.
- **A pull request's CI job doesn't write to the team's runs.** It writes only under `pr/<number>/`; a pull leaves those folders out unless given `--include-pr`, a run brought from one is never pushed back, and nothing such a folder says about a run already here is taken. The CLI only puts those runs in their place: `shadowlap store policy` prints the pull-request policy that makes the cloud enforce it.
- **A pulled fix's patch is someone else's code.** A pull takes a fix only when each repair's patch is the one rewrite its accepted candidate makes, to that candidate's file alone and in place, and `shadowlap fix apply` checks it again before `git apply`, so an edit in the bucket can't make it write any other file. That file is never one of a recording (a pack's `run.json` holds the command a replay of it runs, which `shadowlap test` runs without asking once the repository tracks the pack), nor `shadowlap.config.json` or anything in `.shadowlap`, whatever its case, trailing dots, stream or short name: a recorded command never changes through a repair, which only ever rewrites the text the agent sends the model, where its source holds it. Its confirm dialog shows the patch, and nothing on this machine runs the code it put in (no build, test or replay of your goldens) until you have read it.
- **A pulled fix's steps run only from checked fields, and only after a yes.** A pull marks every blame and verdict it brings as pulled, a mark that stays on this machine. Blame again, Run more attempts and Verify again build their arguments from the report and the flags kept beside it, each a flag Shadowlap allows with a value of its shape, never from a command line the fix carries, and none run again with a value that holds a control or format character or a line or paragraph separator (a pull refuses a fix whose text holds one); a pulled one runs without a teammate's `--build`, `--base` and command after `--`, spends no more than twice what Shadowlap runs by itself (a blame's gate up to 40 attempts and 2 calls probed past its boundary, a verify's gate up to 160 attempts a run, a fixed count up to 10), and runs only once you confirm the exact command line, which the question shows. A pulled step's page offers the command made here to copy, never the one a teammate ran.
- **An edit in the bucket can't change a replay here.** Anyone your cloud admin lets write to the bucket can change a run there, but not how a copy already on your machine replays or whom it names as its author. `shadowlap store check` warns when the bucket keeps no versions, which keep a run's earlier state, or no object lock, which keeps those versions from being deleted.

### MCP

`shadowlap mcp` trusts `SHADOWLAP_URL` only when it is a loopback address. Without it, it takes its run from the file Shadowlap writes for each agent it starts, `~/.shadowlap/agents/<pid>.json` (the project's `.shadowlap/agents` when the home folder can't be written), which carries the session token: the folder is owner-only, and a file is trusted only when it is a regular file you own, readable by you alone, names the process it is filed under and that process's parent, and points at loopback. Where the process tree can't be read, it takes `.shadowlap/active.json` on the same terms, naming a process still running. Started under a Shadowlap command that runs agents but unable to record into its run, it refuses write tools and passes reads through unrecorded; with nothing pointing at Shadowlap, it passes tool calls straight through and says why ([docs/mcp.md](docs/mcp.md#finding-the-run)).

`shadowlap mcp --listen`, which serves the proxy over HTTP, takes only a loopback address, and answers only requests that name that address in `Host` and, from a browser, in `Origin`, so a web page can't reach the server through it. Any process on this machine that can reach the port can, with the `--header` values the proxy holds.

### Telemetry

The CLI sends nothing unless `SHADOWLAP_TELEMETRY_URL` names a collector, and it has no default endpoint. What it would send is listed field by field in [docs/telemetry.md](docs/telemetry.md). They never include prompts, tool names, arguments or results, file paths, hostnames, run ids or model names. The collector installs nothing but Shadowlap's engine, which has no dependencies of its own, and rejects any event with a field outside its allowlist or a value outside its closed sets, and any time before 2025 or more than a day ahead of its own clock. Turn it off with `SHADOWLAP_TELEMETRY=0` or `DO_NOT_TRACK=1`.

## What you should know

Recordings contain **everything your agent saw**: prompts, tool inputs and outputs, and any user data in them. Treat `.shadowlap/` and any pack you export as sensitive.

`shadowlap pack` applies the redaction rules in `shadowlap.config.json` (`shadowlap redact add --pattern email`, a UUID, a `/regex/`, or a path-scoped rule) to every stored request and response in the exported copy; the local store is left untouched. A redacted pack records its rules and still replays cleanly, because the same rules are applied when matching. Redaction is pattern-based: it masks what your rules describe and nothing else, so review a pack before sharing it.

A pack keeps a model's signed reasoning as recorded, whatever the rules (Anthropic's `thinking` and `redacted_thinking` blocks, Gemini's `thoughtSignature`, an OpenAI reasoning item's `encrypted_content` and the like), because a fork sends it back and the provider refuses a block that was changed. What a rule matches inside it leaves with the pack, so `pack` names each rule that does, and the calls. A copy that is only read (an HTML report, a share link, a HAR, a dataset) masks it like any other text.

The network guard (`--guard warn|block`) keeps replays faithful by reporting or refusing connections that bypass the sidecar. It is not a sandbox. A replayed agent runs with your permissions and can still read files, spawn processes and reach the network by other means. Each Node and Python process tells the sidecar when the guard's preload has loaded, so a run the guard never watched says so, and under `--guard block` fails. The Claude Code CLI that the Claude Agent SDK runs loads no preload: the SDK's fence names what that CLI can still reach (WebFetch, an MCP server over the network, a hook or credential helper that isn't Python, its own traffic), and under `--guard block` the run fails unless nothing is left or `guard.accept` takes the CLI as it is ([docs/frameworks.md](docs/frameworks.md#claude-agent-sdk)). The guard can't see a socket a C library opens (libpq under `psycopg`, `mysqlclient`, `grpcio`, Node's native addons): wrap such calls as tools with a `write` effect.

A replay runs again whatever its recording doesn't hold. Every command that replays a run (`replay`, `test`, `blame`, `verify`, `repair`, `calibrate`, `bisect`, `injection`, and recorded tests through `serve --recordings`) refuses to start when the model called a tool the run never recorded that writes, or that nothing says the effect of (a built-in such as `Bash`, a name such as `send_email`, or one the config declares), until it is wrapped, declared a read, or allowed with `--allow-unrecorded` (`SHADOWLAP_ALLOW_UNRECORDED` for recorded tests).

`shadowlap repair` shows a model what the failing runs held, tool output included, through your redaction rules, and verify then builds the agent's prompt from the rewrite it gets back. So a rewrite has to keep exactly the placeholders of the text it replaces and add none, and no quote or backslash beyond what the span it replaces already held: one that brings in `${process.env.GH_TOKEN}` or `{os.environ}`, or a backtick that would end the string literal a span sits in, is set aside before anything runs. A prompt file that is a link counts as the file it names only when that file is inside the repository; a candidate is read from, and written to, the file itself, never through a link out of it. The file is opened without following a link and without being emptied, and written only once it is the file the path, walked again, names, so a folder on the way swapped for a link while repair opens it is refused and what the link led to is left as it was; so is a file with another name, a hard link, which is the same file wherever that name is. A process running as you that rewrites the worktree as repair works crosses no boundary this guards: it could write those files itself. Each candidate is tried in a temporary git worktree, checked out without the repository's hooks, never in your working tree. `--repairer claude-code` runs your Claude Code on that content restricted (`--restricted`, Claude Code 2.1.248 or later), which loads managed settings alone and none of your user, project or local settings, so no hook, permission rule or plugin of theirs runs on it; with no tools (`--tools ''`, `--disallowed-tools 'mcp__*'`), no MCP server (`--strict-mcp-config` with none given), and no session kept on disk (`--no-session-persistence`). Its answer is held to a schema and its system prompt replaced from a file. It signs in with your login or an API key in its environment, never through an `apiKeyHelper` or `env` of your own settings, which it doesn't load. One whose `claude --version` is older is refused before anything is blamed, as is one your organization's `managed-mcp.json` governs, under which Claude Code won't start with no MCP server; an older one that names no version rejects `--restricted` itself.

The GitHub Action installs the CLI from npm without running any package's install script, since the job may hold keys and tokens; a build from source (`build-from-source: true`) runs no install script either and gets none of the job's environment but what npm and Node need, in a home and a temporary folder of its own. No GitHub token the job holds reaches the CLI or the agent it runs: the job's own token, `github-token`, a `GH_TOKEN` in the step's env, the token the job asks GitHub for OIDC tokens with, and any variable that copies one are taken out of what they get. The action pushes a fix's branch with the token in git's environment alone, from a repository of its own made for the push (no config, no hooks, none of git's user and system config) to the repository the workflow runs in, as the runner names it, and only when the checkout's origin names it too, which it checks before a repair spends anything: otherwise it pushes nothing, never to the origin in its place. It opens the pull request through GitHub's API; its steps check out with `persist-credentials: false`. So the token is on no command line and in no file the agent could read, and no hook or remote the agent could leave in the checkout gets it. That bounds where the token goes, not who can take it: while the agent runs, the action's own process holds the tokens in its environment, and on any runner the agent's processes run as the same user, who can read it. The job's `permissions` are the bound on what an agent with a tool that runs code could do with a token. On a pull request it opens a fix only when the pull request is from this repository, never from a fork, and it refuses to test or fix anything on `pull_request_target`, `workflow_run` and `issue_comment`, each of which runs with the base repository's secrets and a token that may write and is how a pull request's code gets run beside them, and on those it neither restores the test history from the cache nor saves the job's store as a branch's. What a run, a model or the agent's source wrote, and what the test history a job restored from the cache says, go into a fix's pull request body, the action's comment and its job summary as text GitHub renders, links and mentions nothing in, so an image, a link or an `@mention` planted in a tool's output shows as it was written and does nothing; the pull request's title is the fix's commit subject, the repairer's one line, on one line and at most 256 characters, with a mention, an issue reference and a workflow command's start split by a word joiner, which shows nothing. Nor does it start a line of the job's log, where the runner would read it as a workflow command (an annotation, `::add-mask::`, or `::stop-commands::`, which would silence the action's own warnings): each line the action writes keeps it on that line, escaped as a command's data is; a line of repair's output that would start one is escaped where it starts, and at each `##[` in it; and `shadowlap test`, whose lines reach the log as it prints them, escapes a failed golden's details, its message and an update's reason the same way.

A store in a repository you cloned is someone else's data, like a pack. A store is normally ignored by git, but a repository can force-add one. Don't replay runs from a checkout you don't trust.
